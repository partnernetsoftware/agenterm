# SYNTHESIS — dynamic-core 研究轨总综合（Q0–Q22）

**这份文件是这条轨的交付物。** 二十二个判决性实验各自成立，但没人读得完二十二份 RESULTS。
这里回答五个问题：**这东西长什么样、贵多少、哪里永远关不上、什么条件下不成立、对北极星意味着什么。**

> **它不是摘要。** 每条结论都可追溯到某个 Q 的 `RESULTS.md`，并带**证据等级**。
> 不可比的数字**不并排**（口径纪律见 [`COMPARABILITY.md`](./COMPARABILITY.md)），该写"未测定"就写"未测定"。

## 初心：一句话，以及它为什么会长成二十二个实验

**这条轨最初的提问方式是"要用上哪些动态技术——JIT、AOT、FFI、mmap"。这个提法本身是需要被纠正的起点，不是终点。**

真正的初心只有一句话：

> **agent 产出的、构建内核时并不知道的逻辑，要能在构建内核时也不知道的机器上正确地跑起来，并且这个过程要可验证。**

它服务的是产品北极星（`plan/design-dynamic-core-experiment.md` 的前置动机）——
「通过 agenterm 工具能 100% 操控自身和所有能控制的资源并获取反馈，未来才能跟大模型自主反馈式自进化」。
这句话如果不能被拆解成可测量的问题，就只是一句口号；**二十二个 Q 就是把它逐词拆开测量的结果**：

| 那句话里的词 | 拆开后要回答的问题 | 谁测的 | 测出来什么 |
|---|---|---|---|
| **"跑起来"** | 需要生成新字节并执行（①②），还是可以只靠链接到机器上已经存在的二进制来解释一份数据（③④⑤）？两者是不是同一件事？ | Q0·Q2·Q9·Q10·Q12 | **不是同一件事，而且分量不对等。** ③④⑤（reach/call/declare，即 FFI/链接）是**每条执行路线都要用、且用法相同**的地基——这不是"动态"，是链接。①②（真正字面意义的"动态生成并执行二进制"）反而是**可选的加速层**，而且是**平台正在收紧的那一层**（ACG/iOS）。解释器只用③④⑤就能跑完整个 IR，从不碰①②——"动态执行二进制"的大部分价值，原来不需要真的动态执行二进制 |
| **"构建内核时也不知道的机器"** | ISA 与 OS 这两根轴，各自能不能在运行时才决定？ | Q0·Q5·Q8·Q12 | **不对称，且是物理性的。** OS 轴能真动态（运行时探测+查表，内核加一个 OS 是 0 字节）；ISA 轴不能（CPU 硬件解码字节），只能造 N 份各自认全部 OS 的小内核，且 N 的边际成本已被量出来是有界的（~300 行/ISA + ~0.6KB 内核，不随 OS/intent 数增长） |
| **"并不知道的逻辑"** | 需要一个能装下未知逻辑、且不预先绑定 ABI/布局的容器——中立 IR 是否真的能中立？ | Q1·Q5·Q7·Q21 | **有边界，边界很精确。** 计算/内存/控制流/单次 OS 调用的**摆放**（寄存器/栈/红区）完全能推迟到降级时决定；**OS 接口的内容**（命名、结构体布局、多步编排里的条件分支）不能中立——因为中立的 OS 调用需要封装，而内核明令禁止封装。这处矛盾是本轨唯一真正"化不开"的两难：封装没有消失，只是从内核搬进了 lowerer/IR，并在那里按 O(目标数×intent 数) 重新长起来 |
| **"可验证"** | agent 产出的逻辑，哪些能被机器验、哪些只能信？ | Q4·Q13·Q14·Q15·Q16·Q17·Q19 | **能验的边界，恰好和"能中立"的边界重合。** 中立核可以用产出时构造门验证（零执行、零额外字节）；intent 边界可以 allow/deny；布局与命名可以用运行时往返自检验证（从静默信任变成 fail-fast）。**边界之外——调出去之后 OS/子进程做了什么——三个轴（产出时/执行时/中立性）在同一个地方一起停下**，这不是巧合，是同一个原因（封装被禁止）的三种表现 |

**这张表存在的意义**：它证明这条轨不是十六个（后来是二十二个）互不相关的问题拼出来的，
**是一句话，用四个词各自展开成一个可测量的子问题**。任何新加的 Q，都应该先问一句：
"它在填这张表的哪一格"——填不进去的实验，大概率是跑偏了。

**校核（本轮整理新增，逐条核实二十二个 Q 是否都落进了这四行）：**

- **Q3（适配器复用）、Q6（原语完备性）、Q18（发现无钦定）、Q20（call 形状边界）四个 Q 不出现
  在这张表里。** 核实后确认这不是遗漏，是范围边界：这四个答的不是"一句话"四个词中的任何一个，
  而是两个**相邻但独立**的问题——第二层（适配器/载荷）怎么复用而不裂片化（Q3·Q18），以及
  ④ `call` 原语本身的数据形状能表达到哪一步（Q6·Q20）。两者都服务同一个产品北极星，但都不是
  这句一心话的分解，本表因此刻意只有四行、不是六行。完整的六族索引（含这两个之外的族）见
  [`README.md`「按初心分组读这张表」](./README.md#按初心分组读这张表)。
- **一处错配，已改正：Q16（组装/接缝审计）原列在"并不知道的逻辑"行，现改列到"可验证"行。**
  "逻辑"行的"测出来什么"一栏描述的从头到尾是 Q1/Q5/Q7/Q21 的封装/L3b 结论，从未提到过
  Q16 的实际产出。Q16 真正测出来的东西（S2：产出时结构等价验证在被迫解释的平台上失效）恰恰
  是"可验证"行头条那句"三个轴（产出时/执行时/中立性）在同一个地方一起停下，这不是巧合"的
  **直接实证**——组装八个部件、真机跑起来，才把这条收敛线暴露出来的，却一直没被列进那一行的
  "谁测的"。这不是文字游戏：Q16 组装的部件里确实包含 Q1 的 IR，但它检验的性质是可验证性
  （能不能在两条不同执行路线上都拿到产出时等价保证），不是中立性本身（IR 能不能装下未知逻辑）。

### 从这张表能直接推出的架构形状

把四行的"测出来什么"接起来，不需要再读二十二份 RESULTS——这个架构最终的样子是可以**直接
推导**出来的。推导链条如下（每一步的出处见前面对应行/后续章节，不重复举证据等级）：

1. **"跑起来"这行 → 解释是地板，JIT/stencil 是有条件加速器，不是反过来。** 生成新字节（①②）
   会被平台拿走，且随平台种数增长的是编码器（307–350 LOC/ISA）；链接/解释（③④⑤）不随 ISA
   数长、不需要可执行内存、对硬化平台的第二道关卡结构免疫。默认能跑的答案必须是解释，JIT 是
   "平台允许时才加的加速层"。
2. **"机器"这行 → 两层，且 ISA 轴造 N 份小核、OS 轴运行时探测。** OS 差异能推迟到运行时
   （查表，加一个 OS = 0 字节），ISA 差异不能（硬件直接解码字节），于是唯一自洽的形状是：
   **冻结的最小内核按 ISA 各构建一份**（N 份，边际成本已量出是有界的：~300 行/ISA + 内核本身
   仅 +13% 量级），**OS 差异全部下沉到运行时装载的适配器/载荷**。这是①里"两层"判决背后的
   物理原因，不是审美选择。
3. **"逻辑"这行 → 中立 IR 的边界就是 OS 接口内容的边界。** 中立 IR 能装下的只到"计算 + 内存
   + 控制流 + 单次 OS 调用的摆放"——这条边界不是实现不够好，是**封装被内核禁止**这条硬约束
   的直接后果：任何跨越它的东西（命名、布局、多步编排）都需要封装才能中立，而封装没地方放，
   只能长在 lowerer/载荷里。载荷层不可能"越写越薄"：O(目标数×intent 数) 的增长是这条边界的
   必然结果，不是当前实现的不足。
4. **"可验证"这行 → 验证边界与中立性边界重合，因为是同一个原因造成的。** 中立核能被产出时
   构造门验证（零执行），是因为它就是第 3 步里"能被中立表示"的那部分；intent 边界之外只能
   信，是因为它就是第 3 步里"不能被中立表示、必须封装"的那部分。可验证性没有一条独立的边界
   ——**它是中立性边界的另一面**。Q16 把八个已判决的部件装到一起、真机跑起来，才把这条重合
   线**实证**出来（产出时等价守卫在被迫解释的平台上失效，根源是"比较两份独立降级"这件事本身
   依赖第 1 步"JIT 是可选的"这个事实——平台一旦不允许 JIT，比较的对象就没了）。

**这四步连起来，就是"给决策者的一页"里那句结论的来处**：两层 + 五条 host-conditional 原语 +
三条后端跑同一份有边界的中立 IR + 验证边界＝中立性边界。二十二个实验测的不是"这个形状该不该
是这个形状"——那句话四个词直接推出这个形状；实验测的是**这个形状具体要付多少代价、在哪些条件
下失效、残留在哪**（②③④）。

**最该记住的四句**：

1. **解释执行是地板，不是退路。** 反转不建立在体积上（那条轴**未测定**），而建立在 **ISA 轴（0 vs 307–350 LOC/ISA）** 与**两道平台关卡**上——这三条是干净的。
2. **封装没有消失，只是搬了家。** Q1 的核心两难：中立的 OS 调用需要封装，而内核禁止封装 → 封装搬进 lowerer/seam，按 O(targets × intents) 重新长出来。Q7 把它压成数据（单次调用族内斜率为 0），Q9 证明它与执行方式正交，但**没人消灭它**——Q17 试图绕过它（递归），结果是缝换了性质、没有缩小。
3. **信任边界是 intent，产出与执行两根轴上都是。** 越过它之后，无论 JIT 还是解释，控制力与观测力都**为零**——除非边界另一侧也是我们自己的 IR（Q17 的窄例外）。
4. **"找解法"这一轮的账**：五个被点名的残留里，**一个消解**（Q18：发现是构建时问题）、**两个精确化收窄**（Q19：S2 的头条收窄到"等价"；Q20：`call` 的形状边界从四项全堵收窄到两项已关）、**一个既精炼又确认死透**（Q21：R1 的线性半区已表化跑通，剩下的精确是"数据依赖的条件控制转移"——这是全轨对"什么东西真的需要图灵完备表达力"给出的最锋利的一条边界）、**一个确认为真·永久**（Q17：intent 边界作为 OS 内容缝，递归证明是搬家不是解法）。

## ① 这东西长什么样

### 1.1 层数与职责

**两层**：冻结的最小内核 + 运行时装载的可替换载荷。

判决依据必须如实给**两种读法**（Q0 §4 的判决树是有 bug 的，规格里漏了 ④ 这个节点）：

- 按 §4 **字面树**（③→②→⑤/⑥，从不列 ④）：**险胜 1 层**，靠 ② 的字节截距（Linux 3104 vs 3496 B）。
- 按 §3 **声明的优先级**（斜率 ③④ 高于截距 ①②）：**2 层**。因为 ④（+1 能力的边际成本）**不打平**：不使用新能力的程序在 2 层里长 **0 字节**（新能力 = 另一个 blob 文件），在真正单产品的 1 层里长 **+~0.4 KB/能力**（`A_fused − A_rhp` = +432 B Linux / +512 B Windows）。⑤（TCB）与 ⑥（并存）同向。

**[真机执行（Windows）；Linux 列仅字节测量] Q0 ②④⑤⑥** — [`RESULTS.md`](./RESULTS.md)

> **诚实条款**：这个 spec bug 已被记进方法论（`.claude/skills/decisive-experiment/SKILL.md` §3「判决树写完必须与 §3 优先级对账」）。不要把"2 层"读成无条件胜出——它赢在斜率，输在字节截距。

| 层 | 职责 | 明确**不**做的事 |
|---|---|---|
| **内核（冻结）** | 五条原语，无跨平台语义 | 没有 `open()`，没有可移植文件模型。文件 I/O 靠 ③+④ 调平台自己的函数 |
| **载荷/适配器** | 全部 OS 语义、全部 intent 内容、全部布局烘焙与自检 | 不观察 ABI 摆放（那是 lowerer 的事） |
| **分发（可选）** | 内容寻址 store + manifest：去重、版本并存、无钦定 | 不提供 name→hash **发现**（③ 残留） |

### 1.2 原语清单 — **五条，host-conditional**

```
① memory    预留/提交/保护（RW ↔ RX）
② execute   把控制权交给一段字节
③ reach     裸 syscall + 符号解析   ← 必须拆成两半，地基完全不同
④ call      按参数的数据描述调用任意原生地址（libffi 模型，整数/指针字子集）
⑤ declare   向宿主查询布局/ABI/机器事实；发布生成代码的事实
```

**[真机执行；字节仅测量] Q6** — [`primitives/RESULTS.md`](./primitives/RESULTS.md)

四条关于这张清单的硬事实：

1. **内核地板稳定（Claim K 成立）。** 三个形状迥异的能力（mmap-file arity 7 / dir arity 2 / socket arity 3）**加 0 内核字节**，且**没有**把 ④ 的 arity 天花板（11）顶上去——Q0 的 7→11 是**一次性台阶，不是每能力的斜率**。**[真机执行] Q6 ①**
2. **完备性 claim 被证伪（Claim R 不成立）。** 「③+④ 够到平台上任何已存在的东西」对**布局类**是假的：`offsetof` 由 ①②③④ 中的**任何一条都产不出来**。`sym` 解析的是**地址**，不是**描述**。**[真机执行] Q6 ②**
3. **⑤ 是否"必要"有两个答案，两个都要报。** **机械上 NO**（Declare 的三个操作都是普通 ③+④ 调用）；**概念上 YES**（"只有做"的四动词模型让这个关切结构性不可见，于是布局常量被反复静默烘焙）。**在内核里给它一个统一查询通道 = +182 B `.text`（550→732，同文件对同命令，+33%）；留作 ③+④ 用法 + 载荷侧烤表 = 0 B。** **[仅字节测量] Q6 ③**
4. **没有第六类内核原语。** 编排 = 载荷侧生成的代码；回调/函数指针 = ①②④ 已覆盖；publish 折进 ⑤。**[结构推断] Q6 ③**

**两条必须写进原语定义的修正**（都来自 Q8 实测）：

- **② 必须多态**：直接 RX / 跨进程共享 section / **解释**。三种"拿到可执行内存"的方式在默认策略下全通、在 ACG 下**全断**（同为 `1655 = ERROR_DYNAMIC_CODE_BLOCKED`）。**解释必须是一等实现，不是给 JIT 形状事后补的补丁。** **[真机执行] Q8 J1/J2**
- **③ 必须拆两半**：裸 syscall（Windows 上按构造不用，Q0 内核 `return -1`）与符号解析（**一等、恒定可用，ACG 完全不碰它**）。R1 把两半合成一条原语，实测显示它们的地基完全不同。**[真机执行] Q8 J6**

### 1.3 执行后端 — 三条路线都建过、都跑过

| 路线 | 体积（**注意口径，绝不同尺**） | ISA 成本 | 第一关：拿可执行内存 | 第二关：硬件肯不肯跑 |
|---|---|---|---|---|
| **解释**（Q9/Q12） | **1908 B** eval-core / **3177 B** 整个解释器 — *口径 S-C：object `.text`，msvc，std+默认 panic；3177 **含** OS intent seam（1269 B）* | **0**（eval-core 的 ISA 相关 LOC = 0，grep 实证） | **不需要**——从不申请 RX | **结构免疫全部四道**（没有生成的字节可供落地/刷新/展开/重定位） |
| **JIT 降级**（Q2/Q12） | **3003 B** — *口径 S-A：flat-PIC blob 相减（code+data），ELF，no_std+`panic=abort`；**不含** OS 层；**该产物从未执行**（执行的是 Windows PE 那条 7680/9216 B）* | **307–350 LOC/ISA** | **被 ACG 全断**（三条路 → 1655） | 硬化 = 发射侧 **+4 B/entry**（ENDBR）、**~34 B/生成函数**（unwind，可暂缓）；**降级器自身增长未测量** |
| **stencil**（Q10/Q12） | **5826 B**（code+data）— *口径 S-B，Q10 刻意逐字复用 Q2 的构建与相减方法，**故这一格与 3003 B 直接可比*** | 数据 + 一段不可约的 per-ISA 代码残留 | **被 ACG 断**（同一条 `VirtualAlloc`/`VirtualProtect` 路，结构性推断，未单独在 ACG 下测） | **放置一碰就炸**（±2 GB `PC32` 孔，Q10 实际撞上并被迫 arena 共置） |

> **size 列不是一把尺。** 只有 JIT 与 stencil 两格同口径。解释器那格在三根轴上同时不同（object `.text` vs flat 相减；std vs `no_std`+`panic=abort`；**含** vs **不含** OS intent 层），**不得与另两格相除**。见 D2 / COMPARABILITY U1·U2。

**判决：默认框架是反的。** 「JIT 主路、解释兜底」被三条**独立**测量掀翻：

1. 解释**与 ISA 无关**（0 vs 307–350 LOC/ISA——降级器的**体量主体就是**解释器根本没有的那个 x86-64 编码器）**[结构推断] Q9 ④ + [结构推断] Q5 ②③**
2. 解释**不需要可执行内存**（ACG 下第一关照过）**[真机执行] Q12 ⑤**
3. 解释**对第二关结构免疫**（这是最硬的一条）**[真机执行+结构推断] Q12 ⑤**

而两条 codegen 路线**要满足的平台越多就越大**——stencil，最完整的 codegen 形态，**比它本该缩小的那个 JIT 还大（5826 vs 3003 B，同口径）**，并且在放置约束上引爆。

> **反转建立在 ISA 轴 + 两道平台关卡上，别的都不靠。** 特别是**不靠单 ISA 字节数**——那条轴按现有文档是**未测定**（D1/D2）。
> **代价必须同时报：计算密集内循环 ≈77× vs 优化原生**（OS 密集载荷 **1.0×**）。**[真机执行] Q9 ③**

**第四条路：AOT。** Q0 的变体 B 载荷本来就是预编译 flat 原生 blob，映射后跳入并在 Windows 上执行；Q8-T1 实测「ACG **启用前**翻成 RX 的内存，启用**后**仍能执行」——"上锁前把代码全铺好"成立，但**之后一个字节都不能再生成**。一次性 AOT 是硬化平台下 codegen 唯一活着的形态。**[真机执行] Q0 + Q8 J5-T1**

> **Q16 的接缝审计（8 部件装成一个二进制，真机跑三载荷）发现全轨唯一的真·不可共存**：Q4 的 Tier-A 结构守卫是**比对两份独立 codegen 降级**的构造门；**纯解释器产零份降级**——在 ACG/iOS 这些**被迫解释**的平台上，守卫无东西可比，从 Tier A 掉到 Tier B（甚至 ACG 下连要比的降级都产不出来，掉到 Tier C）。**架构最强的验证结果（Q4 无执行等价）与最强的可移植结果（解释是硬化地板）在硬化平台上不能同时成立。** Q19 随后证明这条**不是"产出时验证整体缺席"**——解释器路径能有一个更小的 Tier-A **良构**门（见 R8），只是它验的是不同的性质，**等价**这半仍然只属于 codegen 路。**[真机执行] Q16 S2 + Q19**

### 1.4 载荷表示 — 中立 IR，**有边界的中立**

一份类型化三地址 / SSA-lite 寄存器 IR，只有一个值类型 `Word`。**它是一个完整的后端表面**——同一份**逐字节未改**的 IR 被三条后端消费并产出相同语义：

- Q1 降级到 SysV64 与 Win64（`pure_compute` 两边**281 字节恒等**并执行）**[真机执行（Win64）；SysV 仅字节测量] Q1 ①**
- Q5 降级到 aarch64（`spec/ir.rs` 与 `payloads.rs` 与 Q1 **`cmp` 逐字节相同**，零 IR 编辑、无新类型、无 ISA 提示）**[编码器验证（26/26 vs LLVM）；未执行] Q5 ①**
- Q9 解释（三载荷全过，`pure`→163、`rhp`→`a49d2cbecc13994f`、`spawn`→`exit=07`/7）**[真机执行] Q9 ①**
- Q10 stencil（三载荷**字节恒等地**执行）**[真机执行] Q10**

**中立的边界在哪（Q1 的泄漏清单 L1–L5，全轨的头号产物）：**

| # | 泄漏 | 是什么 |
|---|---|---|
| **L1** | 外部引用**不可中立命名** | Win64 是字符串 `"CreateFileA"`，SysV 是 syscall 号 `2`——**不是同一种东西**，绑定表在 lowerer 里且**随 intent 数线性长** |
| **L2** | 语义 arity ≠ 原生 arity，必须注入目标常量 | `FileOpen(path)` 1 个语义参 → `CreateFileA` 7 参 / `open` 3 参。**这是核心两难**：OS 调用的中立性靠封装买来，而封装正是架构禁止的 |
| **L3** | **OS 结构体布局没有中立形**（头号） | `STARTUPINFOA.cb = 104`、`hProcess`@0。`SpawnWait` 因此**塌成一个粗 intent**，两边降级**共享零结构** |
| **L4** | out-param 宽度是布局事实 | `ReadFile` 用 32 位 out DWORD；SysV `read` 直接返回——**同一 intent，一边要 out-param 一边不要** |
| **L5** | 错误/哨兵约定不同 | `(HANDLE)-1` vs 负返回值。中立的"失败了吗"**写不出来** |

**正面结论（NON-leak）：ABI 机制是真能推迟的。** 参数寄存器、溢出顺序、Win64 32 字节影子空间、SysV 红区、返回寄存器**全部从语义签名推导，IR 零参与**，且 `CreateProcessA`（10 参 → 6 个溢出）**跑通**。**[真机执行] Q1 NON-leak**

**ISA 轴上的追加发现**（Q5）：I1 reach 内容是 per-**(ISA,OS)** 不是 per-OS（aarch64-Linux 的 read 是 63 不是 0）；I2 syscall **集合**换形状（aarch64 无 `open`/`fork`）；I3 立即数范围、I4 对齐/偏移缩放是 **NON-leak**（留在 lowerer，只花代码尺寸）；I5 **ABI 摆放轴的形状本身随 ISA 变**——aarch64 上 Linux/Windows 共用 AAPCS64，于是 **Q1 的"ABI 是 per-target"这个结论本身是 ISA 相对的**。**[结构推断/编码器验证] Q5 ⑤**

### 1.5 OS 接缝的最好形态：表驱动（有边界）

对**单次原生调用族**（Alloc/Open/Read/Close/Write），OS 内容**完全变成数据**，跑在一个固定 marshaller 上并**执行**（`pure`→163，`rhp`→`a49d2cbecc13994f`）：

- **+1 intent 的引擎代码增量 = 0；+1 同 ISA target 的引擎代码增量 = 0。** 结构性验证：`grep -c 'abi.name ==' marshal.rs` → **0**；`match .*intent` 只命中一条文档注释。**[真机执行；斜率为结构推断] Q7 ②**
- 数据是 **schema 可校验**的：5 行/目标、0 错误，负面探针（声明 FileOpen arity 0）**被拒**→ 非空转。**[结构推断] Q7 ④**
- 发射字节 ≤ Q1（Win64 rhp **1216** vs Q1 的 1249）。**[真机执行] Q7 ③**

**但它停在哪：**（a）**L3b 编排/控制流**——多调用数据流、SysV `fork` 后按 pid 分支，**没有任何扁平表能表达一个分支**；（b）**I2 跨 ISA 重构**。`spawn_boundary()` 分类：**可作数据 1 / 需查询通道 2 / 不可约地是代码 5**。**[结构推断] Q7 ⑤**

> **引用纪律**：Q7 的引擎**根本不做 spawn**（`SpawnWait` 不在两张表里，marshaller 无法降级它），Q1 的每目标 90–110 LOC **恰恰包含** spawn。"70 LOC 固定 vs 90–110 LOC/target"**不是 like-for-like**。正确形式：**在单次调用族内**，Q7 = 固定 70–112 LOC 引擎 + **每目标 57–58 LOC 数据**；Q1 = **每目标 90–110 LOC 代码**（且含 spawn）。**斜率结论不受影响**——那才是 Q7 的产品。见 COMPARABILITY U4。

## ③ 哪里永远关不上

**七条永久残留。** 每一条都不是"还没做"，是"这个架构里没有能补它的东西"。

### R1 — 控制流编排（L3b） ✅ **Q21 已判决：精炼而非推翻，全轨最锋利的一条边界**

Q7 当年把五个 `SpawnWait` 事实一并打成"不可约的代码"，**但从未真正去表化这个序列**。Q21 拆开来发现根本不是一类问题：**两个是直线数据流**（每步永远都跑，只是参数值不同，如取 `hProcess`、四步顺序执行）；**三个共享同一个根因**——由运行时值决定"要不要跑/跑几次"（`fork` 的 pid 分叉、argv 运行时长度、错误哨兵判断）。
**线性那半被真的建出来并跑通**：一张纯数据步骤表（`ArgSrc` 枚举，固定分派循环里**零 `if`**，grep 核实），驱动真实 Windows 4 步 `SpawnWait` 链，真机跑通 `cmd.exe /c exit 7` → 读回退出码 7，`hProcess` 提取折进参数解析而非需要分支。
**墙是被执行出来证明的，不是断言的**：同一张表指向一个不存在的路径，schema 里没有任何字段能表达"跳过 Wait/GetExitCode"，静默报出假的退出码 0——那次失败**就是**表化到头的证据。
**精确的缺失能力**：由运行时值决定的条件控制转移——一旦把它加进 schema，schema 就有了可执行程序的操作语义，**和这条轨自己的 IR 没有结构性区别**。没有发明小语言然后骗自己说它是数据。
**结论**：Windows `SpawnWait` happy-path 的**线性链 100% 可表化**（跑通，非论证）；不可表化的**精确是**数据依赖的分支/循环，**不是**"编排"这个大类，也**不是**"Windows 4 步 vs Linux 3 步"这个平台差异本身（一条假想的、无分叉的 3 步 SysV 链会同样被表化）。
**[真机执行] Q21 ①②③④**

多调用数据流（从 `PROCESS_INFORMATION` 取 `hProcess` 喂给下一个调用）、以及**条件分支**（SysV `fork` 后按 pid 走两条路）。
**没有任何扁平表能表达一个分支**；把它塞进数据 = 发明一门调用序列字节码 = **IDL 滑坡**，这正是实验设计来检测的病。
`spawn_boundary()` 的八项分类里，**不可约地是代码的有 5 项**。
**没有任何原语能补它**——Q6 复跑了"找一个任何原语都够不到的事实"这个方法，结论是编排属于**载荷侧生成的代码**，不是内核类。
**[结构推断] Q7 ⑤ + [真机执行] Q6 ③**

### R2 — 跨 ISA 重构（I2）

aarch64-Linux **没有 `open`**（须 `openat(AT_FDCWD, …)`），**没有 `fork`**（须 `clone`，其参数顺序本身是 arch 相关的）。
**同一个 intent 跨 ISA 不是换号，是重构**——arity 变、语义变、序列变。换号可以表化；重构不行。它是 **L3b 戴着 L1 的面具**。
这是 ANDF「预算烧在长尾上」的具体机制。
**[编码器验证；未执行] Q5 I2 + [结构推断] Q7 ⑤**

### R3 — 命名绑定真值 ✅ **Q14 已判决：结构上仍不可查，但行为式（Tier B）可验且收敛**

「符号 index 1 **是不是真的** `CreateFileA`」「syscall 2 **是不是真的** `open`」「`0x8000_0000` **是不是真的** `GENERIC_READ`」——
**schema 校验配方的形状（产出时、无执行），永远校验不了它的命名真值。** 这一条**依然成立**：Q4 的结构守卫（Tier A）够不到命名。
但 Q4 曾据此断言「命名的后果正是你要确立其正确性的那个东西，**没有独立探针**」——**这个强判定被 Q14 推翻**：
对**有契约的符号**独立探针**存在**，即一个「已知入→已知出」的**外部**神谕（字符串长度 / 算术 / 写进去的字节），DLL 无权定义它。
Q14 实测四个绑定全部「正确绑定 PASS / 故意绑错 FIRE」（`lstrlenA`/`MulDiv`/`lstrcmpiA` 纯函数 + `CreateFileA` 往返簇），
且**循环收敛**：一个对**有契约符号**说谎的 resolver 会被该符号自己的检查抓到，链条**触底于残留类**而非符号表——
**{Thompson trigger, 无契约符号, 内核}**。有契约载荷的**残留信任命名绑定 N≈0**。
**Thompson 只在这个残留里活下来**（测试期诚实、运行期恶意），不再是整条命名轴。
**残留精确表**：无可观测契约的符号（`OutputDebugStringA`/`ExitProcess`）、弱/间接可观测（`Sleep`，只能 modulo 另一符号）、以及 Thompson trigger。
**代价**：纯函数检查 8 LOC/符号、往返簇 40 LOC，**内核 +0 字节**（Q13 同信封）。
**[结构推断] Q4 ④ L1 + Q7 ④ + [真机执行] Q13 ⑤ + [真机执行] Q14 ①②④⑤**

> **判决口径（诚实条款）**：Q14 的验证是 **Tier B——需要执行**（把符号真的调一遍，且有副作用），**不是** Tier A 的产出时结构验证。
> 所以**产出时**命名仍不可验（Q4/Q13 在「结构上不可查」这点上没错），只是「不可查」不等于「不可约的信任」——
> 命名从 **Tier C（纯信任）** 上移到 **Tier B（运行时可验、可收敛）**。R3 因此**不再是全轨最后一个不可检测的信任洞**；
> 剩下的真·残留是 Thompson trigger 与无契约符号，二者是本平台**任何**验证方案都已背着的。见 [`naming/RESULTS.md`](./naming/RESULTS.md)。

### R4 — 无语义往返的布局字段

Windows **没有运行时 `offsetof` 神谕**（`GetSystemInfo` 发布机器事实的**值**，但每个值藏在宿主不发布的偏移后 = **自举循环**；真神谕需要 PDB = 被排除的病理），所以**烤不可免**。
**但错烤可检测**：Q6 三个布局事实**全部**在故意改坏的偏移上触发 ③+④-only 自检（构造式文件名回读 / socket `bind`+`getsockname` 往返 → WSAEAFNOSUPPORT 10047 / `GetSystemInfo` 交叉字段）。**bake-and-pray → bake-and-detect。**

**残留是**：**没有语义往返的字段**——只写不校验的 flags、不可预测读（`WIN32_FIND_DATAA.ftCreationTime`）、松校验的 `cb`（`STARTUPINFOA.cb=104`）。那些字段**永久**是静默信任。
并且检测有**强度梯度**：构造式与往返式严密 *modulo 命名*；**交叉字段弱**——它自举于**其它烤进去的偏移**（这次实测抓到作者自己烤错的 32 位-vs-x64 偏移，正好证明了这个弱点的两面）。
**[真机执行] Q13 ①②④**

### R5 — intent 边界之外（**最要紧的一条**）

`spawner` 载荷的危险内容（`cmd.exe /c exit 7`）**根本不是 IR 值**——rodata = **0 字节**，`SpawnWait` extern nargs = **0**。它活在 IR **之下**的 seam 里，**没有任何 `Val` 可供 taint/allowlist/bounds 去 gate**。
允许 `SpawnWait` 之后，`CreateProcessA` 一进 kernel32，子进程自由运行；解释器**只拿回一个退出码 `Ok(7)`**。子进程读写文件、开网络、再 spawn——**零观测、零约束**。
**控制点是 intent 那一层的 allow/deny，过了它什么都没有。** 而这一层 **JIT 与解释代价相同（都是 O(1)，同一个 chokepoint）**。
**[真机执行] Q15 ②④**

### R6 — ④ 的形状边界（不是 arity，是形状） ✅ **Q20 已判决：有意义地收窄，非一致解决**

float/SIMD 参数、struct-by-value、varargs、`sret` —— 原判定是**在任何 arity 下都表达不了**。这不是斜率问题，是 ④ 的整数/指针字子集本身的边界。
**Q20 逐项检验后，四项拆成了三种命运**：
- **float：已关闭。** 给签名描述加一个 `Int`/`Float` 的 `Kind` 标签，走**同一个**摆放轴（Q1 已证明可推迟的那条——寄存器/影子空间/红区），只需 ~12–16 行，**不需要新原语**。真机跑通 `sqrt`/`pow`/`ldexp`（后者是决定性用例：float 在前、int 在后，朴素照搬 SysV 分计数规则会**静默算错**——Win64 的按位置规则由宿主 codegen 保证正确）。
- **struct-by-value ≤寄存器宽度：已关闭，0 行增量**——一旦调用方把字段顺序烤进去，走的是**未改动**的原有基线（落进已知的 offsetof 类残留，不是新洞）。`PtInRect`（`POINT` 按值传）真机跑通双向正确。
- **struct-by-value >寄存器宽度 / `sret`：诚实留空。** 推理上可用 Q1 已有的"常量参注入"机制关闭，但搜遍 kernel32/user32/gdi32/msvcrt/常见 POSIX libc，**没找到一个真实系统 API 需要它**（系统 API 几乎全按指针传结构体）——**没有证据就不强行判"关闭"**。
- **varargs：一分为二**——任何有限/静态形状**已关闭**（每个具体调用点就是另一条按数据分类的调用）；**真正运行时决定形状的部分永久残留**（IR 的 `Call` arity 在编写期就是静态的）。
- SIMD 设计上不在范围内，不下判定。
连带后果仍在：载荷必须手搓格式化（十六进制循环、两位十进制循环），这是可测的表达力税——**但已从"四项全堵"收窄到"两项已关、一项分裂、一项诚实开放"**。
**[真机执行] Q6 ① caveat + [真机执行] Q20 ①②③④ + [结构推断] Q1 ④**

### R7 — 内容寻址的"发现"缺口 ✅ **Q18 已判决：消解为构建时关注点，非运行时残留**

内容寻址给的是完整性 + 去重 + 版本并存，**没有 name→hash 方向**——装载器回答不了"文件适配器是哪一个"，只能取一个你已经握着的哈希。
这一半仍然成立。但 R7 曾被读作"运行时的洞，钦定从这里重新进来"——**这个读法被 Q18 推翻**：

**① 无钦定的运行时形态确实存在**：两个消费者用**互不冲突**的目录，把**同一个 name** `fileio` 解析到**不同 hash**（v1 全读/v2 截断），**都正确并同时运行**（真机实测，`len=0023` vs `len=0008`）。无默认目录、无全局兜底（目录缺该名 → 退出 23，不静默转向权威源）——版本并存判别式通过：单一注册表**无法表达**"fileio 既是 v1 又是 v2、取决于谁问"，per-consumer 目录天然可以。
**⑤ 更强的结果**：把 name→hash 完全**上移到构建期**（谁写 manifest 谁一次性解析并冻结），运行时**零发现代码**，产出**同样两个分叉结果**——`loader_hash` 与 Q3 装载器逐字节相同（2672 B）。**发现根本不是内在的运行时问题。**
残留是**局部、多元、可选**的信任（你信你选的那个目录/哈希源），**不是**"唯一、共享、强制"。唯一不可约的一点——这个哈希是否真如名字承诺的那样行为——属于**命名真值（R3/Q14）**，与发现/钦定正交。
另外它去重的是**字节，不是行为**：同源不同 `-O` 等级 → **同一哈希**（可复现构建让"同源→同享"成立）；行为等价但实现不同（循环读 vs 一次读）→ **不同哈希，去重失效**。
**[真机执行（Windows）；字节为 Linux 仅测量] Q3 ④ + [真机执行] Q18 ①②③④⑤**

### R8 — 结构不可验的那一块（Q4 的天花板）

结构性等价守卫覆盖中立核 + 控制 + 机制，**唯独盖不住 intent 区段**——而 intent 区段就是 L1–L5。
不可验分数：**`pure_compute` 0% → `read_hash_print` 29.3–40.8% → `spawn_echo` 44.8–55.6%**。
**`spawn_echo` 的 Win64 像里超过一半没有任何结构性等价可言。**
更下面一层：**L5 在原理上不可判定**——中立的"失败了吗"这个谓词写不出来，于是**要检查的那个等价关系本身无法陈述**（Tier C）。
**[结构推断] Q4 ②④**

> **Q19 的边界（解法尝试，部分成功）**：Q4 验的是**等价**（一对制品的**关系**性质，需要 ≥2 个独立执行体）——纯解释器只有**一个**执行体，等价**结构性拿不到**（Q16 §S2）。Q19 造了一个 **98 LOC / 634 B** 的 IR **良构**验证器（同样 Tier A：产出时/无需执行/构造门/不可遗忘），三个真载荷 PASS、五种注入坏 IR 全 FIRE。但良构是**一元**性质，和等价**不是同一个保证**：三个刻意构造的良构-但-危险案例全部 **PASS 通过**——`oob_store`（PASS，**良构 ≠ 内存安全**，正是 eBPF 花 2 万行的地方）、`Exit 999`（PASS，**良构 ≠ 语义正确**）、`spawn` 的 `cmd.exe /c exit 7`（不是 IR 值，rodata=0，L1–L5 缝原样在）。**净效果**：产出时轴在解释器地板上**不是空的**（良构验证在），但**等价**验证仍然结构性缺席——**S2 的头条存活，重新限定到"等价"，而不是笼统的"产出时验证"**。**[真机执行] Q19 ①②③④**

> **Q22 的补充发现（组装暴露，非孤立实验能测到）**：把 Q19 的良构验证器和 Q7/Q21 的表驱动编组器真的装进同一个二进制后，浮出一条新缝——**Q19 的验证器只检查 IR 内部的 arity 一致性，对编组表自己的 arity 契约一无所知**。一个用 1 个参数调 3 参 `FileWrite` 的 IR **能通过 `verify()`**，然后在解释器里**因为下标越界而 panic**（已用 `catch_unwind` 捕获并报告，没有悄悄打补丁掩盖）。**这是良构验证的边界在"单一部件内部良构"和"跨部件契约一致"之间又长出的一条缝**，与 R8 主文的"良构 ≠ 等价、≠ 内存安全"是同一类问题的第三个实例：**"良构"这个词本身也需要说清楚是对谁而言的良构**。**[真机执行] Q22 ②F1**

> **Q23 的追加（F1 契约能否在加载时声明——本条引 [`runtime-intent/RESULTS.md`](./runtime-intent/RESULTS.md)，非在本文件重测）**：把 Q22 的 F1 修法（`contract_arity()` 编译期 match）搬到 pack 加载时，实测得一个**判决性的拆分**——F1 的两半命运相反。**内部 arity/内存安全那半能干净地搬到加载时，但必须"从 recipe 推导、而不是另立声明"**：一个真机从未随 nativecore 出厂的 kernel32 导出（`MulDiv`→15、`lstrlenA`→5）**纯靠运行时文本 pack + 通用 ④ trampoline 跑通，零重编译零 codegen**；欠参的 IR 只在契约**由 seam 会解引用的那份 recipe 推导出来**时才被执行前拦下（`IntentArityMismatch{provided:2,contract:3}`），而一个**另立的 declared arity 字段会原样重开 F1**（作者同时握着 IR 和声明＝单作者自证循环，正是编译期 `contract_arity()` 靠"第二方"打断的那个圈）。**但 ABI 那半搬不动（诚实负结论）**：一个把真 3 参 `MulDiv` 声明成 1 参的 pack 内部自洽、`verify()` 放行、trampoline 用 1 参调它读到垃圾寄存器返回 1 而非 15——**单作者数据 pack 里没有任何东西能让 `verify()` 知道真 arity 是 3**（Windows x64 导出无可查询的 ABI 元数据，是 Q1-L2 ∩ Q14 残留，不是新洞）。关键澄清：**`contract_arity()` 从来也没机器验证过这半**，它只是一个读过 WriteFile 契约的人写下的常量——**重编译真正买到的是"第二方对真实签名的独立断言"（经 git+人审），不是一道 F1 机器检查**。Q14 的行为式探针（direction 2）在运行时（Tier B）为**有契约符号**追回绑定正确性（把 `lstrcmpiA` 冒充 strlen 的错绑打成 FIRE，got -1 ≠ 5），残留与 Q14 完全一致，**外加一条新边界：探针强度 ≤ 被声明的签名**，故它抓错绑、不抓 arity 的欠声明。指出的中间路：一张人审一次的**签名注册表**（签注册表而非签二进制）能在不为每个新 intent 重编译的前提下恢复那个第二方断言。**[真机执行] Q23**

## ④ 什么条件下不成立

### C1 — 平台硬化（第一关）

Windows 默认策略 `DynamicCode = 0x0`，**ACG 是逐进程 opt-in、默认关**，三条拿可执行内存的路（RW→RX 翻转 / 直接 RWX / section 对象映射）全通、都真跳进去返回 42。
**ACG 一开，三条全断，同为 1655**（R1 §7.1 说"断两条"，**实测更强：三条**）。
- 对**我方自有进程**：缺口是**策略可配置**的（我们可以不开）。
- 对**别人以 ACG 托管我方代码**：进程内**无合法自救**，除非启用时带了 `AllowThreadOptOut`。
- 两条有条件窗口实测成立：**前置 RX 存活**（一次性 AOT）、**AllowThreadOptOut + 线程退出**。
- **跨进程 JIT 未实现**（超时间盒）。

**[真机执行] Q8 J1–J5**。ACG 可由 WDAC/AppLocker/EXE 头/父进程创建属性**外部强加** = **[转述未验]**（本机未构造该场景）。

### C2 — 平台硬化（第二关）

**本机 x86_64 上没有一条第二关真的咬今天的产物**，但这个结论的**前提很窄**，必须一起引用：

- `CPUID.7.0` 报 **CET_SS=0 / CET_IBT=0**——**本机硅片根本没有 CET**（不是"支持但没开"）。
- **Windows 没有前向边 IBT 的运行时开关**（不像 ACG），所以**无法"开启再测"**——判据是实跳测试而非查文档。这是方法学限制，不是清白证明。
- 三个产物的 `ENDBR64` 计数全 **0**；Q2 的两类间接跳转目标都没有落地垫；四种模式（P0/P0b/P1-entry/P2-callback）**全过、全返回 42**。
- 生成帧 `RtlLookupFunctionEntry` = **NULL**（未注册 unwind），**潜伏未触发**——当前载荷不穿帧展开。
- I-cache 在 x86 **免费**。
- **±2 GB 放置截断是真的，且是最坏形态：实测静默**——>2GB 的 `call rel32`（3GB delta）经 Q2 逐字相同的 `as i32` 截断，**发射/回填零报错**，跳到诱饵 → **返回 99 而非 42，无崩溃**。
  **但 Q2 结构上免疫**（OS 调用走绝对间接 `call [r15+idx*8]`，rel32 只在 <8 KB 缓冲内部，**从不发射指向外部符号的 PC 相对引用**）。**任何转向 copy-and-patch 的改动会当场引爆**——Q10 已经实际撞上。

**[真机执行] Q12 ①②③⑤**。**ARM BTI / arm64e PAC / ARM `IC/DSB/ISB` 跨线程协议 = [转述未验]**（无 ARM 硬件）。

### C4 — 负载性质

## ⑤ 对北极星意味着什么

> 用户的目标原文：**「通过 agenterm 工具能 100% 操控自身和所有能控制的资源并获取反馈，未来才能跟大模型自主反馈式自进化」**

综合必须回答的是：**agent 产出的东西，哪些能被机器验、哪些只能信、边界在哪。**

### 5.1 信任图（Q4 产出时 × Q13 布局 × Q15 执行时，三轴合并）

| 代码段 | **产出时**（Q4 结构守卫，Tier A/无执行） | **布局+命名事实**（Q13 布局 × Q14 命名，Tier B/自检） | **执行时**（Q15 控制点） | 合并 |
|---|---|---|---|---|
| **中立核**（算术/内存/控制流） | **Tier A/A′（codegen 路）**：中立区段字节恒等（246/676/623 B 跨目标相同）；篡改一个中立字节 → `build` 返回 `Err`，**产不出可运行字节**。**无需执行、无需第二个 OS、产物 0 额外字节**。⚠️ **限定（Q16/Q19）：这是"等价"验证，需要 ≥2 份 codegen 降级——纯解释器地板上结构性拿不到**；解释器路径有一个**更小的、不同的** Tier-A 门（良构，98 LOC/634 B），验的是单一制品的良构而非跨制品等价，见 R8 | n/a | 指令层可拦**越界 / 步数上限 / 分配预算**（**O(1) 共享代码**；JIT 要 **O(ops) emit guard 字节**或一个装载时验证器） | ✅ **codegen 路两轴都盖住**（产出时验等价 + 执行时保封闭）；**解释器地板产出时轴收窄为良构，等价那半空缺**，执行时轴不受影响 |
| **intent 边界**（准不准调 OS） | **部分**：配方 schema 可校验（Q7 ④，5 行/目标 0 错误，负面探针被拒）；**符号绑定真值结构上仍 trust**（Tier A 够不到命名） | **可检测（布局+命名皆可）**：布局有语义往返的字段 fail-fast（Q13，~18–38 LOC/事实）；**命名对有契约符号亦可行为式验证**（Q14，8 LOC/纯符号、40 LOC/往返簇，皆 0 内核字节，正确 PASS/绑错 FIRE）。**{命名+布局} → {无契约符号 + Thompson trigger + 内核}**，有契约载荷残留命名绑定 **N≈0** | **可 gate，但只是 allow/deny**（O(1)，**两条路同价，JIT 无劣势**） | ⚠️ **阀门；但绑定真值不再是洞**——布局+命名（有契约）已从信任集移出，Tier B |
| **intent 之外**（L1–L5：调出去之后 OS/子进程干什么） | **洞**：结构不可验分数 0% pure → 29–41% file-I/O → **45–56% spawn** | n/a | **洞**：控制力 = **零**。危险内容不是 IR 值（rodata 0 B、extern nargs 0），只拿回一个退出码 | ❌ **两轴同一个洞** |

**收敛（全轨最强的一条）：产出时的结构守卫与执行时的解释控制点，恰好在同一个地方停下；而 Q13 把布局、Q14 把命名（有契约）先后从洞里捞出来之后，剩下的洞完全一致——OS 接口内容（L1–L5），调出去之后。**
这是**同一条缝在两根不同的轴（产出 / 执行）上各自现身，且都关不上**。要关它只能封装 OS 调用，而封装被内核禁止（Q1 的核心两难：封装不会消失，只会搬进 lowerer/seam 并按 O(targets × intents) regrow）。

> **Q17 净改动（递归 / 自托管边界）——"边界之外只能信"有一个有边界的例外。** 当且仅当边界另一侧是**我们自己产出的中立 IR（跑在另一个核实例上）**时，观测在另一侧**协作式**重新成立：核 A 可以 (a) **产出时结构验证**子任务 IR（Q4，不可遗忘），(b) 从核 B 拿到**逐 intent 运行时轨迹**（B 自报、B 用同一个 O(1) chokepoint 自我管控）。残留信任从"信任整个不透明被调方"**收窄**到 **{信任 B 的解释器二进制（Thompson/R3）+ 产出时验证 M_B}**。**但递归不缩小 OS 内容缝**——L2–L5 原封搬进 B，另加一道**净新增的 A↔B 信道缝**（固定编解码、中立词表；其 L1 半边被中立化，优于 Q1 的 per-target disjoint 符号表）。**对外来二进制/原生库（cmd.exe、原生 .dll），"只能信"不变。** 代价：每层一个进程（本机 ~11 ms/层，字节 210–286 B——延迟昂贵、字节廉价）。**故 intent 边界作为 OS 内容缝是真·永久残留（Q17 确认 R5 方向，递归只搬家不缩小）；作为 A↔子任务的观测壁垒，递归把它从不透明转成协作式可观测——那是可观测性的改善，不是缝的缩小，也不是强制式观测。** 直接支撑 5.3 第 4 条"边界之外的可观测性必须来自 IR 之外"：递归证明了在 IR 层继续找缩小这道缝的解法是搬家，该接受它。**[真机执行] Q17 ①②④** — [`recursive/RESULTS.md`](./recursive/RESULTS.md)

> **Q14 对本图的净改动（诚实条款）**：绑定真值这一栏——曾被 Q13 记为「布局可验、**命名仍 trust**」——现在**命名也是 Tier B 可验**（对有契约符号），信任集从 **{命名 + 布局}** 收窄到 **{无契约符号 + Thompson trigger + 内核}**。但**限于执行时（Tier B）**：**产出时**（Q4 那一栏，无执行）命名依旧够不到——所以「绑定真值不再是洞」这句只对**运行时**成立，产出时它仍是 trust。真·残留（Thompson + 无契约 + 内核）是本平台任何验证方案都已背着的。

**[结构推断] Q4 ②④⑤ + [真机执行] Q13 ⑤ + [真机执行] Q14 ①④⑤ + [真机执行] Q15 ⑤**

### 5.2 对"100% 操控 + 获取反馈"的直接回答

| 断言 | 判定 |
|---|---|
| **agent 产出的计算逻辑可以被机器验** | ✅ **成立**，且是**构造门**（不是事后检查，忘不掉）、**不需要执行**、**产物 0 额外字节**。这是本轨最干净的正面结论。 |
| **agent 产出的 OS 交互可以被机器验** | ⚠️ **分层，比旧结论宽**。**产出时（无执行）不成立**——只有**配方形状**（schema）可结构验；命名与布局的绑定真值 Tier A 都够不到。**执行时（Tier B）大幅成立**：布局偏移效果（Q13 往返自检）与**命名绑定真值**（Q14 行为式验证，对有契约符号）都可 fail-fast 验，残留收窄到 **{无契约符号 + Thompson trigger + 内核}**。仍不可验的是 **编排/控制流不可表化**（R1）与产出时的命名（需执行）。**旧结论「命名绑定真值不可验」已被 Q14 修正为「结构上不可查、行为式（运行时）可验且收敛」。** |
| **执行时能拦住 agent 代码作恶** | ⚠️ **半对，且错在要紧那半**。指令层（内存安全 / 可终止性 / 资源上限）**真能拦，且便宜**（1.47×、+1027 B），JIT 要付 O(ops) guard 或一个 20,065 行的验证器（本轨核只有几 KB，**二者不可兼得**）。**但那一层 agent 伤的是自己进程**。真正的危险面（调出去之后）在 intent 边界之外，**那里两条路控制点相同、且都控制不到边界外**。 |
| **能 100% 获取反馈** | ❌ **不成立**。过了 intent 边界，反馈信道**只剩返回值**（`Ok(7)`）。子进程做了什么、OS 做了什么，**零观测**。 |

### 5.3 因此，自进化回路应该把验证力气花在哪

这不是本轨测过的东西，但它是从上面三张表直接读出来的**架构约束**，写在这里以免被误读：

1. **IR 内的东西，用构造门（Q4 形态）验。** 便宜、无需执行、不可遗忘。
2. **布局事实，用往返自检（Q13 形态）验；命名绑定，用行为契约自检（Q14 形态）验。** 都 0 内核字节，都把静默信任改成 fail-fast——纯函数用外部神谕（长度/算术）、OS 符号用往返簇、绑错即报警。**但都是 Tier B（要执行）**，产出时够不到。**把"无语义往返的字段"与"无契约的符号"显式记进设计文档**——那是已知的（运行时也）静默信任残留，连同 Thompson trigger。
3. **intent 层做 allow/deny，别指望它做内容控制。** 解释器与 JIT 在这一层**同价**，选哪条路都不影响安全性。
4. **边界之外的可观测性必须来自 IR 之外**（进程/OS 级观测），因为 IR 里根本没有那些值。**在 IR 层加更多策略机制不会改善这一点**——Q15 已经把这条测死了。
5. **别把"解释更安全"当作选型理由。** 选解释的理由是 **ISA 轴 + 两道平台关卡**，不是安全，也不是（未测定的）单 ISA 体积。

## 发现的矛盾与文档不一致

按纪律，如实列出，**不挑一个当真理**。

### X1 — Q7 的 L3a 出路在 Windows 上没有落点（**条件性冲突，非直接矛盾**）

- **Q7 ⑤ 说**：L3（结构体布局）的**布局半边 L3a 能表化**——以**查询形式**，表里带名字 `("STARTUPINFOA","cb")`，宿主**布局神谕**回答，绑定时折入。
- **Q13 ① 说**：Windows 上**不存在**运行时 `offsetof` 神谕；`GetSystemInfo` 只发布**值**，而每个值藏在宿主不发布的偏移后（**自举循环**）；真神谕需要 PDB = 被排除的病理。
- **Q6 ② 说**：Windows 系统结构体**没有**机器可读的布局发布，该事实**不可约地被烤**。

**不是打架**（Q7 自己声明它的神谕是**桩**，且措辞是"需要一条查询通道"），但**向上引用时极易被读成"L3a 已经解决了"**。
**正确的合并读法**：*L3a 的形状是查询式的，且在 Linux（BTF/CO-RE）上有落点；在 Windows 上没有查询通道，只能烤——而 Q13 用检测替代了查询。* 三份 RESULTS 拼起来才是完整答案，单引 Q7 会过度乐观。

### X6 — Q3 内容寻址与 Q4 等价守卫站在不兼容的生命周期点（Q16 §S4，新增）

### X4 — 「内核基线」在本轨有两个相差 14 B 的实例，文档没有指定用哪个
