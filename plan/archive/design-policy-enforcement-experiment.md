## §0 背景与已定事项（不在本实验重议）

北极星是**自我进化**：由 LLM/agent 产出能力。那么「agent 产出的东西在哪里跑、在哪里能被拦住」
是硬约束。已确定：

1. **[Q9]** 解释器是 Q1 中立 IR 的**完整后端**：逐字节同一份 IR，`run` 走 op-by-op，eval-core 55 LOC / 1908 B。
2. **[Q9/Q1]** IR 通过 `Intent`（Alloc/FileOpen/FileRead/FileClose/WriteStdout/SpawnWait）调 OS；这些 intent 落到
   `do_intent` 一个分发点，再经 FFI 调真实 kernel32。L1–L5 缝全在 intent 之外（`do_intent` 之后）。
3. **[Q4]** **产出时**有结构性等价守卫（构造门），覆盖中立核，intent 区域是关不上的洞（0% pure → ~30–56% spawn）。
4. **[Q12⑤]** 解释路线对四道「落地关」结构免疫（不生成可执行字节）。这是**可用性/健壮性**结论，**不是安全性**结论。
5. **审稿已认定**：Q9 测体积/速度/覆盖，Q12 测硬化平台可运行——**都是「可用性」，不是「安全性」**。
   「解释器更安全」**从未被测量**。本实验就是来补这一刀的。

**本实验只问执行时控制点，不重议 1–4。**

## §1 硬约束（违反则实验无效）

1. **复用不改造**：IR（`ir/spec/ir.rs`）与解释器 eval-core（`interp/interp.rs`）**逐字节复用**，不改一行。
   策略检查作为**外挂的一层**（新文件），不得混进被复用的核。若必须改核才能加检查——**那本身是发现，记下来**。
2. **对照必须是同一份 IR 的两条执行路**：解释 vs JIT（Q1/Q2 lowerer）。不得用两套不同的 IR，否则把
   「执行方式差异」和「IR 差异」混在一起——测不出控制力来自哪侧。
3. **② 的判据是「intent 边界之外还有没有控制力」**：必须用一个**真的调出去**的载荷（SpawnWait 起子进程）
   实测，看解释器能不能约束子进程干什么。不是读文档、是真跑。
4. **③ 必须拆开记**：per-instruction 检查的**斜率**（每多一条指令/每多一个内存 op 的边际检查代价）与
   解释器体积的**截距**（相对 1908 B eval-core 的增量），两者分开。只报「今天多大」= 没量。
5. **④ 必须给 JIT 路线的对照数**：同一策略，JIT 要付什么（emit 出的 guard 字节 / 装载时验证器 / 还是做不到）。
   这一条是「解释是否有结构性安全优势」的**正面回答**，缺了整个实验作废。

### §1.1 病灶探测器（本实验要检测的病，不是要满足的需求）

> **任何为了「拦得更全」而滑向 <做沙箱 / 做权限系统 / 设计策略 DSL / 写 eBPF 式装载时验证器> 的冲动，
> 是本实验要检测的病。** 要的是**控制点在哪、代价多少**这个判定，不是一套安全机制。
> 一旦发现自己在设计策略语言或权限模型——**停下，记为发现**（正是 §4.1 eBPF 20k 行的教训：装载时验证器
> 与「几 KB 的核」不可兼得），不要偷偷加。策略检查保持在「一个 `if` + 一个计数器 + 一张 intent 允许表」
> 这个最小可用量级，够触发判据即止。

## §2 最小实验内容

| 维度 | 选了什么 | 为什么这样选 |
|------|---------|-------------|
| 执行后端 | 解释器（Q9 eval-core）为主，JIT（Q1 win64 lowerer）为对照 | 隔离变量：同一 IR，只动执行方式 |
| 策略类（①） | 4 类：**内存越界** / **资源上限**（步数+分配字节）/ **OS 调用面**（intent 允许表）/ **数据流**（污点） | 覆盖规格建议的四维；数据流故意放进来，因为它是「能不能拦住某值流向某调用」的试金石 |
| 危险载荷（②） | 恶意 IR 变体：越界写 / 死循环 / 巨额 Alloc / 调被禁 intent / **允许 SpawnWait 后子进程自由** | 每个负面测试触发一类检查；最后一个专门证明 intent 之外无控制 |
| 代价（③） | 策略解释器 vs 纯解释器（Q9）在 pure_compute 上的 × 倍数；`.text` 字节增量 | 斜率（每 op 检查）+ 截距（体积），对齐 Q9 的 77×/1908 B 基线 |
| JIT 对照（④） | 同样 4 类策略，逐类判定 JIT 要 emit 的 guard 字节 / 需不需要装载时验证器 / 能不能做到 | 正面回答结构性优势问题 |
| 平台 | Windows Server 2022 / x86_64 真机 | 与全轨一致；SpawnWait 真起 `cmd.exe` |

## §3 判据表（事前钉死，事后不改）

| 判据 | 内容 | 性质 | 判定方式 |
|------|------|------|---------|
| **①** | 逐类判定解释器能否施加：内存越界 / 资源上限 / OS 调用面 / 数据流。产出**一张分类表**（每类：能/不能/部分，控制点在指令层还是 intent 层） | 清单 | 每类一个负面测试：恶意 IR 必须被解释器**拦下**（返回策略违规而非产生效果）；数据流类如实标「部分」 |
| **②** | **（主判据之一）** intent 边界**之外**，解释器还有没有控制力？ | 布尔 | 允许 SpawnWait，起真子进程，判定解释器能否约束子进程行为。**预期：不能**——控制点在 intent 那一层，不在指令层 |
| **③** | per-instruction 检查开销（× vs Q9 纯解释 baseline）+ 解释器体积增量（B vs 1908） | 斜率+截距 | pure_compute 计时比值；`llvm-size` `.text` 差 |
| **④** | **（主判据之一）** 同样 4 类策略在 JIT 路线上的代价：emit guard 字节（O(ops)? O(1)?）/ 装载时验证器 / 做不到 | 安全/对照 | 逐类：解释器 guard 是 O(1) 共享代码还是 O(ops)？JIT 呢？给字节级对照 |
| **⑤** | Q4（产出时构造门）+ Q15（执行时控制点）合并信任图：覆盖了什么、还剩什么洞 | 清单 | 画一张两轴（产出时/执行时 × 中立核/intent/intent 之外）覆盖表 |

**度量纪律**：产物 `rustc -O` release，`llvm-size` 读 `.text`；LOC 去空行纯注释；每个数字复跑命令写进
`RESULTS.md`；负面测试必须给出「不加检查会发生什么」的对照（证明检查非空转）。

## §4 判决树 + kill criterion + 时间盒

**性质优先级**：主判据 = **②+④**（安全/对照）> ③（代价）> ①（清单，是 ②④ 的前置事实）。

```
主判据 = ② ∧ ④。

1. 若 ② 显示解释器在 intent 边界外无控制力
   ∧ ④ 显示 JIT 用「差不多的代价」也能施加同样的（对危险面有效的）策略
   → 判决：「解释无安全优势，只有可用性优势」。编排者被纠正。这是本实验最有价值的可能结论。

2. 若 ② 显示 intent 外无控制力
   ∧ ④ 显示 JIT 要付「高得多的代价 / 装载时验证器 / 根本做不到」才能施加 per-instruction 策略
   → 判决：「解释有结构性安全优势」——但必须限定在**它有优势的那层**（指令层封闭性），
      并如实说明：若该层不是危险面所在（危险面在 intent 外），优势是**有限/错层**的。

3. ② 与 ④ 给出方向一致但代价居中 → 判「有优势但代价过高」，报代价数。

③ 只调整「优势值不值」，不决定「有没有」。① 是清单前置，不单独判决。
⑤ 是合并产物，不参与判负，但必须画出。

kill criterion: 若解释器**连指令层策略都施加不了**（负面测试拦不下越界/死循环）
   → 命题（解释器可作策略执行点）当场证伪，立即停，写结论。

时间盒: 做到 ①②③④ 四项**各出一个可判定结果**为止。
   在此之前**不做**：沙箱、权限模型、策略 DSL、eBPF 式验证器、形式化、第二 ISA、性能优化。
   ④ 的 JIT 对照允许「结构性论证 + 字节级估算」，**不要求真的把 guard 全 emit 出来**——
   只要 O(1) vs O(ops) 的形状被一个可复算的字节数钉死即可。
```

**判决树对账（照 skill §3）**：
- 枚举：①②③④⑤ 全在树里出现——①（清单前置）、②④（主判据节点 1–3）、③（节点末「值不值」）、⑤（合并产物，显式说明不参与判负）。✓
- 对账：树的分支顺序 = 性质优先级（安全 ②④ > 截距/斜率 ③ > 清单 ①）。✓
- 穷举：② 布尔 × ④ 三档（等价代价 / 高代价 / 做不到）的组合，节点 1/2/3 全有出口；② 若显示「有控制力」
  则落 kill 反面（解释器确实是控制点）走节点 2/3。✓

## §6 已排除的选项

| 选项 | 为什么排除 |
|------|-----------|
| 做真沙箱 / seccomp / job object | §1.1 病灶：要的是「控制点在哪」，不是安全机制 |
| 设计策略 DSL / 权限语言 | 同上，且是 §4.1 eBPF 20k 行的直接教训 |
| 写装载时验证器（eBPF 式） | 那是 JIT 路线为拿回控制点要付的代价——本实验**量它**，不实现它 |
| 把污点做成完整信息流分析 | 数据流类只需判「部分覆盖 + 在哪失效」，完整分析是范围爆炸 |
| 第二 ISA / 性能优化 | 与控制点判定无关，时间盒禁止 |

## §7 本实验不回答什么

- 不回答「该用什么策略」（策略内容是产品决策，不是本实验）。
- 不回答 intent 之外如何拿回控制（那要沙箱/OS 机制，是另一条轨）。
- 不回答 ARM/其它平台（无硬件）。
- 不实现装载时验证器（只估其代价作 ④ 对照）。
