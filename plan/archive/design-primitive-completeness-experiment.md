## 0. 背景与要回答的问题

Q0 §1.1 的完备性论证（原文）：

> ①+② 给出「产生新代码并执行」；③+④ 给出「够到平台上任何已存在的东西」。
> 两组合起来没有够不到的东西，**所以内核永远没有"为覆盖某能力而变大"的理由**。

这条论证现在有三份**相互独立的反面证据**：

1. **Q0 自己的 ④(b2)**：加第二个能力（spawn）时，`CreateProcessA` 要 10 个参数，
   逼着把 ④ `call` 的参数上限 7→11，两个变体的内核都因此变大。当时判为
   "一次性台阶，不是斜率"——**是判断，没测过**。
2. **Q7 实测**：L3a（OS 结构体布局）**能**表驱动，但**只能是查询式 + 宿主布局神谕**，
   即需要**第五类 Declare**。四原语全是"做"，`dlsym` 把符号解析成地址，
   **回答不了 `offsetof`，再多 dlsym 也不行**。
3. **技术综述经验旁证**：Drawbridge/Gramine/WASI 三个独立团队都收敛到 **30–50 条**宿主原语。

### 已经确定、不在本实验讨论范围内的事（编号）

1. Q0 已判决 2 层、Q5 已判决 N×M→N（ISA 轴地板稳）。本实验**不重开层数/ISA 之争**。
2. Q8 已判决：原语 ①②（可执行内存）在 Windows 默认可用、ACG 下断；③ 拆成
   裸 syscall / 符号解析两半。本实验**沿用**，不重测执行地基。
3. Q7 已判决：单原生调用族的 OS 内容可全表驱动；L3b 编排/控制流是永久 code 残留。
   本实验**不重测表驱动**，只测"四原语能不能够到 layout"。

## 1. 硬约束（违反则实验无效）

### 1.1 只用 Q0 的四原语实现新能力

新能力（见 §2）**只能经 ③ 符号解析 + ④ 调用 + ①② 内存**实现，
**不许**给内核加任何新的跨平台语义 API。四原语的契约照抄 `core/kernel.rs`：
`mem_alloc`/`mem_protect`/`raw_syscall`/`sym`/`call`。

### 1.2 病灶探测器

**任何"为方便"往内核加第五类原语、或悄悄扩 ④ 参数上限的冲动，是本实验要*检测*的病，
不是要满足的需求。** 若某能力真的够不到某样东西，**记为发现**，明确写出"它够不到什么、
为什么四原语够不到、代价转移到了哪里"，**不许偷偷加原语或偷偷扩 ④ 来粉饰"四原语够用"**。
反过来也**不许为显得有发现而虚构必要性**——每一条"必需"都要能被构造演示。

### 1.3 判据在写代码前钉死

§3 的判据表事后不得改。度量纪律见 §3。

## 2. 最小实验内容

刻意做小到能做完，又刚好能量出斜率。挑**参数个数与结构形状差异最大**的三个新能力，
落在与 Q0/Q7 已测（file-I/O、spawn）**不重叠**的形状上：

| 新能力 | 原生调用（Win64） | 最大 arity | 需要的结构体布局 |
|--------|-------------------|-----------|------------------|
| **A. 内存映射文件** | `CreateFileA`(7)/`CreateFileMappingA`(6)/`MapViewOfFile`(5)/`Unmap`/`CloseHandle` | **7** | **无**（MapView 直接返回文件字节指针）——纯 ④ 对照组 |
| **B. 目录遍历** | `FindFirstFileA`(2)/`FindNextFileA`(2)/`FindClose`(1) | **2** | `WIN32_FIND_DATAA.cFileName @44`（**读**） |
| **C. 网络 socket** | `WSAStartup`(2)/`socket`(3)/`bind`(3)/`closesocket`(1) | **3** | `sockaddr_in.{sin_family@0,sin_port@2,sin_addr@4}`（**写**） |

**为什么这样选**：arity 跨度 2→7（都 ≤ 现上限 11），形状从"零布局纯调用"到"读大结构体某字段"
到"写多字段小结构体"。这个组合能同时压测两件事：**(i) ④ 的参数上限会不会又被逼扩**（主判据 ①），
**(ii) 四原语能不能够到 layout**（判据 ②）。

- **ISA**：只做 x86_64（ISA 轴非本次；见 §0-1）。
- **OS**：Windows 真跑（本机），Linux 侧只做字节测量+形状分析（本机无 WSL，沿用全轨惯例）。
- **执行验证**：三个能力在 Windows 上**真跑**（列目录、映射读哈希、bind 回环），不是只看返回码。

## 3. 判据（**动手前认，事后不得改**）

> 命题是关于**增长曲线**的。斜率优先于截距。

| # | 判据 | 度量方法 | 性质 |
|---|------|----------|------|
| **①** | **④ 参数上限：台阶还是斜率** | 三个形状迥异的新能力，逐个记录每个原生调用的 arity，取**最大值**。**布尔门**：是否有任何能力把 ④ 的上限逼过现值 11？ | **斜率（决定性）** |
| **②** | **Declare 是否真必需** | 对 B、C 的结构体字段访问：能否在**不加第五类原语**下解决？逐条把每个 layout 事实分类为 `{可烘焙常量 \| 需宿主神谕 \| 够不到}`，并**实跑证明**四原语带烘焙常量能跑通。判定它是"必需"还是"可转移" | **布尔 + 清单** |
| **③** | **若加 Declare，地板变多大** | 实现一个 `declare` 原语（Describe 半：`GetSystemInfo` 查页大小；Query-layout 半：查表），量**内核内字节 + 行数增量**，与 Q0 568 B / Q5 644 B 对照。并**用 ① 的方法**再加能力测"有没有第六类" | 截距 + 斜率 |
| **④** | **完备性论证的修订版** | 给出封闭清单（几条）+ 新完备性论证；或明确"无法给出封闭清单" | 清单 |

### 度量纪律

- 字节数取编译产物（`rustc -O`），记录编译器与 flag；③ 的内核字节增量用 `--emit obj` 的 `.text` 增量测，
  明确标注这是"增量"而非与 568/644 同一构建的绝对值。
- "改动行数"不含测试与文档。
- 每个数字第三方可复跑，命令写进 `RESULTS.md`。
- **拆开记**：内核内增长 vs 内核外（载荷/适配器）增长——两者含义相反。

## 4. 判决树 + kill criterion + 时间盒

**主判据 = ①（斜率）。**

```
1. ① 布尔门：加完 3 个形状迥异能力后，④ 的参数上限被逼过 11 吗？
   · 若"每加一类能力都要动 ④/内核" → ④ 是第五种增长源、藏在内核里 → §1.1 判负（地板蠕变）。
   · 若"没有被逼过 11（一次性台阶成立）" → ④ 的 arity 地板稳 → 落 ②。
2. ② 布尔门：四原语（带烘焙常量）能跑通 B、C 吗？其 layout 事实里，有没有
   "既不能烘焙、也无宿主神谕可查"的？
   · 有"够不到"的事实 → Claim R（"没有够不到的东西"）被证伪 → §1.1 判负。
   · 全部可烘焙/可查 → 判定"必需 vs 可转移"，量 ③。
3. ③：Declare 的内核内地板增量；再加能力看有没有第六类。
4. ④：据 ①②③ 给修订完备性论证。
kill criterion：若 ① 逼过 11 且每能力都逼 → 立即判"地板蠕变（④ 是隐藏斜率）"，停，写结论。
时间盒：出 ①②③④ 四个数/判定即停。不做第二个 ISA、不做优化、不做完整 POSIX 覆盖。
```

**判决树 vs §3 优先级对账**：① 斜率优先（主）；② 布尔门决定 Claim R；③ 截距/斜率；④ 清单。
四个判据都在树里是节点，顺序 = 性质优先级（斜率→布尔→截距→清单）。

## 6. 已排除的选项（不要重新提出）

| 选项 | 为什么排除 |
|------|-----------|
| 把 offsetof 硬塞进 ④ 的签名描述 | 那是把 layout 混进 call，正是 ARM64EC 教训（ABI 与 layout 不可分开推迟）要检测的病；且不回答"四原语够不够" |
| 为保住"4"这个数把 Declare 拆进 ③ | §1.2 明禁的粉饰。诚实的五条 > 粉饰的四条 |
| 做完整 socket/POSIX 覆盖 | 滑向 WASI/PAL 的 30–50 条膨胀，正是本命题拒绝的。要的是"地板稳不稳"判定，不是完整宿主接口 |
| 第二个 ISA / 优化 | 超时间盒；ISA 轴由 Q5 处理 |

- ACG/iOS 下的执行地基——Q8 已判。
