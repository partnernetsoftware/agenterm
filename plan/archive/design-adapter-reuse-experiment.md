# 适配包复用：不封装的可移植性工作能否被复用而不被钦定？（历史规格）

> ⚠️ **不是 AgenTerm 产品范围。** 独立研究轨，实现落在 `research/dynamic-core/reuse/`。
> 承接 [`design-dynamic-core-experiment.md`](design-dynamic-core-experiment.md) §7
> 的第三个未解问题（「第二层的组合机制」）。不进任何版本 plan，不改 `PRD.md` 能力状态。

| 字段 | 值 |
|------|-----|
| **日期** | 2026-08-08 |
| **目的** | 用可测量的证据判定「适配包能否被**复用**（而不只是并存），且不需要一个中央注册表来钦定谁是正版」 |
| **前置** | 层数已判 **2 层**；四原语 + 不封装纪律抑制增长（与分层正交）；Q0 的 ⑥ 只证明了「能并存」，**没证明「能复用」** |

## 0. 为什么这是这条路上最难、且真正未解的问题

「不封装」把可移植性工作**转移**了而非消灭：每个载荷得自己面对 Linux vs Windows。
在 Q0 的实测里这具体化为**适配器**（`adapters/{linux,windows}/readfile.rs` 等），
而变体 B 的每个载荷 blob **把它所用的适配器静态编进自己**——
于是两个都读文件的载荷，**各带一份文件适配器的字节**。

**这正是碎片化的具象：一百个人写一百份文件适配器，互不复用。**
这是 JVM「标准垄断 + 体积单向增长」的**镜像失败**——不是垄断，是碎片化，而且目前完全没解。

Q0 的 ⑥（版本可并存性）两个变体都判 YES，但那只证明了「同机能放两份不打架」，
**没证明「两个载荷能共用同一份」**。**并存 + 不复用 = 碎片化。**
本实验要正面量的就是这条缝：**能复用吗？代价是什么？不钦定还能复用吗？**

### 待检验假设（可推翻，推翻价值更高）

**内容寻址**（适配包按其内容哈希命名）可能同时给出复用与去中心：无中央注册表、
天然去重、版本并存自动成立、「谁是正版」根本不存在。**代价未知**：解析成本、
发现问题（不知道 hash 就找不到）、语义等价的两份实现哈希不同 → 去重失效。
**当成假设检验，不是结论。** 若找到更好机制或证明它在这里行不通，价值更高。

### 已经确定、不在本实验讨论范围内的事

1. 层数 = 2；抑制增长的是四原语 + 不封装，与本实验正交。
2. Q0 的度量口径（strip 后 release 字节、x86_64、in-kernel / out-of-kernel 拆分、
   Windows 实跑 / Linux 交叉量字节、无 WSL）**全部沿用**，换了就不可比。

## 1. 硬约束（违反则实验无效）

### 1.1 不得引入注册表 / 依赖求解 / 包管理器

**这是本实验最该警惕的失败模式。** 机制只能是「按内容定位 + 加载」的**最小可行形态**：

- **禁止**：中央注册表、名字→制品的映射服务、版本区间求解、依赖图求解、CLI 包工具。
- **允许**：一个**内容寻址存储**（目录，文件名 = 其内容哈希）+ 一份**清单**
  （载荷自带的一串哈希，声明它要哪些制品）+ 一个**加载器**（读清单 → 按哈希打开文件 →
  映射 → 装配）。加载器对适配器数量必须是 **O(1) 代码**（一个循环，不是每适配器一段代码）。

> **一旦发现自己在写解析算法 / 版本协商 / 名字消歧，立即停下重读本节。**
> 那是包管理器，不是本实验要的东西。

### 1.2 复用必须是「共享同一份字节」，不是「各编一份恰好相同」

判据 ① 要量的是：两个载荷都要文件能力时，那份适配器的字节在磁盘上出现**一次**还是**两次**。
Q0 变体 B 的现状是两次（baked-in）。本实验的机制若不能让它变成一次，**就是没解决复用**。

### 1.3 不得为复用而往内核加第五类原语

加载器读存储用的是 Q0 已有的③④（raw_syscall / sym+call）直接够到文件，**不新增原语**。
内容寻址存储用的哈希是**构建期**算好写进文件名的（存储外部性质），加载器最小形态
**不重算哈希**（信任存储）；若要「按内容验证」（完整性），须把一个哈希函数拉进内核——
这笔代价单列在判据③里量，**不得偷偷计入或漏计**。

### 1.4 复用既有语义，最多造一个最小新载荷

复用 Q0 的 `read_hash_print`（读文件→哈希→打印）语义。为制造「两个载荷需要同一适配」，
**允许造一个最小新载荷** `read_len`（读文件→打印字节数十六进制）——它与 rhp 需要**同一份**
文件适配器（`read_file` + `write_stdout`），是最干净的复用场景。不造第三个能力进复用机制。

## 2. 最小实验：让两个载荷共用一份文件适配器

| 维度 | 选择 | 理由 |
|------|------|------|
| **能力** | 只做文件 I/O 适配器 `{ read_file, write_stdout }` | Q0 已验证的路径；两个载荷都需要它，触发复用 |
| **载荷** | `read_hash_print`（复用）+ `read_len`（新，最小） | 都要**同一份**文件适配器 → 制造复用场景 |
| **ISA/OS** | x86_64；Windows 实跑 + Linux 交叉量字节 | 沿用 Q0 |
| **机制** | 内容寻址存储 + 清单 + 加载器（§1.1 允许的最小形态） | 检验假设 |

### 机制形状（实现者可微调，须满足 §1）

- **适配器 blob**：入口（偏移 0）`fn(out: *mut FileCaps)`，把自身函数指针写进调用者给的表。
- **载荷 blob**：入口 `fn(k: *const Kernel, caps: *const FileCaps) -> !`。
- **存储**：`store/<hash>.bin`，文件名 = 内容哈希（构建期算）。
- **清单**：加载器自带的一串哈希（首个 = 载荷逻辑 blob，其余 = 适配器 blob）。
- **加载器**（= 内核变体，受测机制）：读清单 → 逐哈希 `store/<hash>` 读入（用③④）→
  映射 RX → 调适配器入口填 `FileCaps` → 加载载荷 → 传 `(Kernel, caps)` 跳入。
- **基线**（对照 = Q0 变体 B 现状）：`logic + adapter` 编在同一 blob（baked-in）。

## 3. 判据（**动手前认，事后不得改**）

> 必须能量到**复用**而不只是**并存**。①是复用的字节证据，②是「复用 + 并存」能否同时成立，
> ③是机制自身代价（Q0 口径），④是内容寻址最可疑的一环（无注册表下的发现/解析）。

| # | 判据 | 度量方法 | 性质 |
|---|------|----------|------|
| **①** | **复用/去重（字节）** | {rhp, read_len} 都要文件适配器时，磁盘总字节：**基线**（各 baked 一份）vs **内容寻址**（logic×2 + 适配器×1）。复用成立 ⟺ 内容寻址总字节 < 基线**且**适配器字节恰好出现一次。给出省下的字节，及随载荷数 N 的斜率（基线 N×适配器 vs 1×适配器） | **决定性（字节）** |
| **②** | **不兼容版本 + 复用共存** | 造 `fileio v1`（全量读）与 `fileio v2`（截断读，破坏性行为差异）。rhp 绑 v1、read_len 绑 v2。内容寻址下：两哈希都在存储、都加载、各自输出正确、互不影响 = 是/否；并记两适配器共存的磁盘代价。对照：名字方案（"fileio"）会逼一个胜出（钦定）或版本协商（包管理器） | **决定性（布尔 + 字节）** |
| **③** | **机制自身代价（Q0 口径）** | 内容寻址加载器 vs Q0 单 blob 加载器：**in-kernel** 新增字节 + 行数（解析哈希 + 多 blob 加载 + 填表 + 读存储的③④组合），拆「不验证」与「按内容验证」（后者把哈希函数拉进 TCB）两档；**out-of-kernel**：清单格式 + 适配器入口 glue | 斜率 + 截距 |
| **④** | **无注册表的发现/解析** | (a) 解析成本：每个唯一适配器的**文件打开次数 + 读入字节**，及每载荷**清单**字节；(b) 发现缺口（具体demo）：字节相同的两份适配器**自动去重**（同哈希），行为等价但字节不同的两份**去不了重**（异哈希）——假设自己警告的那条限制，用真实哈希实测 | 量化 + 边界 |

### 度量纪律

- 字节一律 strip 后 release；编译器/flag 沿用 Q0（写进 `RESULTS.md`）。
- ③ 的行数不含测试与文档；in/out-of-kernel 拆分沿用 Q0。
- 每个数字第三方可复跑，命令写进 `RESULTS.md`。
- Windows 实跑验证正确性；Linux 交叉编译只量字节（无 WSL），诚实标注。

## 4. 判决规则与 kill criterion

**事前写死。**

1. **① 是决定性门。** 若内容寻址总字节 **不 <** 基线（适配器没真共享到磁盘上一份），
   则机制没交付复用 → 判**「此机制未解决碎片化」**，立即停、写结论。
2. ① 过 → 复用为真；**② 决定它是「复用 + 可并存」（要的）还是「复用但逼钦定」**。
   ② 若不能让不兼容版本共存并各自正确 → 机制退回「要复用就得钦定一个版本」= 碎片化换了个形式。
3. **③ 定价，且含 kill criterion**：若 in-kernel 代价**随适配器数量增长**（不是常数），
   则机制本身是向外增长 → 按 Q0 ③ 同样逻辑**判负**。加载器 in-kernel 必须对适配器数 O(1)。
4. **④ 报边界，触发诚实条款**：若去重只对**字节相同**成立、对**行为等价**不成立，
   则如实报「内容寻址复用的是**相同制品**，不是**等价实现**」——有边界的成功，照报。
5. **时间盒**：量出 ①–④ 我定的那几个数即停。**不做第三个能力、不做优化、不做 CLI、
   不做版本求解。** 一旦在写解析算法就停下重读 §1.1。

### 失败模式警告

- **滑向包管理器**（§1.1）：最可能的死法。机制 = 哈希→文件→映射→装配，不多一分。
- **把「并存」当「复用」交差**：Q0 ⑥ 已给并存，本实验不复述并存，只量复用（①）。

## 7. 本实验**不**回答

- **谁来填充存储、谁来分发哈希**（发现层）。内容寻址给完整性/去重/并存，**不给**名字→哈希的发现；
  发现需要另一层命名，而那层正是「钦定」重新潜入之处。本实验量到这条边界为止，不设计发现层。
- **可验证性 / diverse double-compilation**（同一 IR 经不同路径降级须行为等价）。独立问题。
- **中立 IR 形状**（Q1 在跑）、**降级放核内/核外**（Q3 在跑）。不碰。
- **跨进程共享映射**（一份适配器在多进程间共享物理页）。本实验量磁盘复用（一份字节），
  运行时跨进程页共享是 OS 加载器话题，超范围。

## 8. 实验结论回填（2026-08-08，实测）

实现落在 `research/dynamic-core/reuse/`；完整数字与复跑命令见该目录 `RESULTS.md`。
Windows 实跑验证、Linux 交叉量字节（无 WSL，沿用 Q0）。以下是回填要点与偏离。

### 判决：复用可达，有一条发现边界（内容寻址假设**基本成立**）

按 §4 判决树逐步走：

1. **① 决定性门 → PASS。** {rhp, read_len} 都要文件适配器时，内容寻址存储把适配器存
   **一份**（`store/aaf8…`，552 B(W)/232 B(L)），基线（baked）各带一份存**两份**。
   N=2 时 CA 总字节 < 基线（1058<1274 L；1378<1912 W），且省下的量**随载荷数 N 线性增长**
   （适配器计 1× vs N×）。**复用为真，字节说话。** Q0 ⑥ 的「并存」从未证明这点——两个 baked
   blob 并存，但**各带一份适配器** = 并存而不复用 = 本实验要测的碎片化。
2. **② → YES（复用 + 可并存，正是要的性质）。** v1（全读）/v2（截断读）两个不兼容版本按不同
   哈希共存于存储，rhp 绑 v1、read_len 绑 v2，**三个程序同时正确运行**（`a49d2cbecc13994f`、
   `len=0023`、`len=0008`），**无注册表、无钦定、无版本协商**。名字方案则必须钦定一个或上求解器。
3. **③ 定价，且过 kill criterion。** 内容寻址加载器比 Q0 embed 加载器 **in-kernel +609 B**
   （Linux 净值，非验证）；**按内容验证**再 **+1648 B**（把 FNV-1a/64 拉进 TCB；SHA-256 更大）。
   关键：加载器对适配器数 **O(1)**（一个循环，加第 3、4 个适配器**零**新增内核代码）→
   **机制本身不向外增长**，不判负。
4. **④ 边界（触发诚实条款）。** 解析 = `1(清单)+(1 载荷+A 适配器)` 次文件打开 + 每程序 33 B 清单。
   去重限制**双向实测**：同源不同 opt 级 → **同哈希**（构建确定性 → 独立构建者自动共享）；
   行为等价但实现不同（循环读）→ **异哈希**（去重失效）。且内容寻址**无 name→hash 发现方向**。

**净结论：复用可达（① pass），且是「复用 + 无钦定并存」（② yes），代价有界且不随适配器数增长（③）。
碎片化不是「无解」——它被从「N 份互不兼容、无法共享的拷贝」转化为「字节相同者自动共享，字节相异者
无害并存」。仍未解的是发现（name→hash），而那正是「钦定」会重新潜入之处——本实验按 §7 止步于此。**

### 与规格不符之处（必然有）

1. **Windows 实跑 / Linux 交叉量字节**（无 WSL），同 Q0。机制在 Windows 跑通；去重是**结构性**
   （同内容→同文件名），与 OS 无关。
2. **哈希用 FNV-1a/64 而非 SHA-256**：内容寻址与哈希无关；紧凑内建哈希让验证加载器的度量成为
   **下界**——密码学哈希只增大 ③ 的「验证」一列，已明写。
3. **④(b) opt 级探针量到的是确定性、不是分歧**（同源两 opt 级 → 同哈希），把朴素预期反转为
   内容寻址的**正面**发现；等价而非同一的情形改用真正不同的实现（`v1alt` 循环读）证得。
   推翻预期，如实记。
4. **未加第五类原语、未加新原语种类**：加载器用已有 ③④ 够到存储；复用机制加的是**打包**
   （存储 + 清单 + caps 表），不是内核原语。§1.1 警告的「滑向包管理器」**未发生**——
   加载器 = 哈希→文件→映射→装配，对适配器数 O(1)。
5. **加载器是通用冻结二进制**（读 `manifest.txt`），非每程序一份，强于规格建议的每程序内嵌清单，
   且保住 Q0 ⑤ 的冻结 TCB 性质，让「一个程序」= 纯数据。
6. **freestanding-MSVC 小插曲（已解决，不留税）**：初版加载器的越界检查触发 `panic_bounds_check`
   （Linux 直链 lld 无法解析）与 MSVC 的 `_fltused`/`__CxxFrameHandler3`。改为无越界检查索引后
   两者皆消失，无需 stub——③ 的 Windows/Linux 数字均为干净值。
