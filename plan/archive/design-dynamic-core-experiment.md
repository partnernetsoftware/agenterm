## 0. 背景与要回答的问题

产品命题（用户 2026-08-08 定调）：**用最小的资源做最大的信息与操作**，
明确拒绝 JVM/JRT/JAR 那条「标准垄断 + 体积单向增长」的路。

由此推出的核心结构问题——**动态核该分几层？**

- **1 层**：机制与平台适配同为一个产物
- **2 层**：极小且冻结的内核 + 可替换、可缺席的载荷空间

推理已经走到极限，两边都有站得住的论证（见 §6 已排除的选项）。**再论证下去没有新信息，
必须做出来量。**

### 已经确定、不在本实验讨论范围内的事

1. **两根轴的不对称是物理性的**：OS 轴可以真动态（运行时探测 + 查表，Cosmopolitan 已证明）；
   ISA 轴不能——**CPU 用硬件解码字节**，已装入内存的代码无法"探测后适配"。
2. **内核只为它自己所在的机器生成代码**。交叉编译是"把字节写进文件"，是普通载荷能力，
   不是内核能力。所以内核尺寸**不随 ISA 数增长**，只是构建 N 份。
3. **接口而非封装**：内核提供**可达性**，不提供**语义**。
   封装（POSIX/JVM/WASI）的膨胀机制是——抽象一旦漏掉某能力，唯一修法是把抽象做大，
   于是单向增长。只给接口没有这个反馈回路。

## 1. 硬约束（违反则实验无效）

### 1.1 内核只有四类原语，不多一条

```
① 内存   reserve / commit / protect (RW ↔ RX)
② 跳转   把控制权交给一段内存里的字节
③ 可达   raw syscall + 符号解析 (dlsym / GetProcAddress)
④ 调用   按一份「签名描述」调任意原生地址（libffi 模型；描述是数据）
```

**完备性论证**：① + ② 给出「产生新代码并执行」（图灵完备的自我扩展）；
③ + ④ 给出「够到平台上任何已存在的东西」。两组合起来没有够不到的东西，
**所以内核永远没有"为覆盖某能力而变大"的理由**。

> ⚠️ **这段论证已被 Q6 实测部分证伪（2026-08-08）。** 它把两件事混为一谈了：
> **够到一个地址**（③ 做得到，成立）与**够到一份描述**（`offsetof` / `sizeof` /
> ABI / 页大小——**没有任何"做"的动词能产出它**）。`sym` 把符号解析成地址，
> 再多 `sym` 也回答不了 `offsetof`。
>
> 拆开后的诚实结论是**两条地板、方向相反**：
> - **内核地板稳定**（字节 / 参数上限 / 原语条数）——上面那句「内核永不为覆盖能力而变大」
>   **仍然成立**。Q6 加了三个形状迥异的能力（内存映射文件 / 目录遍历 / socket bind），
>   最大参数数 7 ≤ 现有上限 11，**Q0 §8 ④(b2) 担心的"斜率"不存在，那是一次性台阶**。
> - **「没有够不到的东西」这句被证伪**（针对布局类事实）。封闭清单是 **五条，且 host-conditional**：
>   ①内存 ②执行 ③可达 ④调用 **⑤ declare（发布 + 询问）**——
>   闭合当且仅当宿主发布这些描述（如 Linux BTF），否则 ⑤ 退化为**烤进去的信任**。
>
> 「Declare 算不算第五原语」有两种都站得住的读法，一并记录：**机制上不算**
> （它就是 ③+④ 指向 `GetSystemInfo` / `RtlAddFunctionTable` / BTF，可实现为零内核字节）；
> **概念上算**（纯"做"的模型让元数据这件事**结构性不可见**，这正是布局常量一再被
> 悄悄烤进代码、并在平台版本变动时崩掉的原因）。
>
> 详见 [`design-primitive-completeness-experiment.md`](design-primitive-completeness-experiment.md)
> 与 `research/dynamic-core/primitives/RESULTS.md`。此处保留原文不改写，
> 是为了让后来者看到论证**原本错在哪**——按本轨方法论，规格有 bug 就标注修正，
> 不在结论里绕过去。

④ 是承重墙：有了它内核**什么都不用实现**。要文件？调平台自己的函数。

> **任何"为了方便"往内核加第五类原语的冲动，都是这个实验要检测的病，不是要满足的需求。**
> 真需要就记录下来当作发现，不要偷偷加。

### 1.2 禁止封装

内核不得提供任何跨平台**语义** API。不许有 `open()`、不许有"可移植文件抽象"。
只能有 §1.1 的四条。平台差异一律由载荷承担。

### 1.3 两个打包版本必须共用同一份实现

**不写两个原型。** 写一份可分离的实现，打包两次：

- **变体 A（1 层）**：全部静态链进一个产物
- **变体 B（2 层）**：保留边界，适配运行时加载

**已知偏差，必须在报告里复述**：按可分离方式写，内部设计已经偏向 2 层；
真正的 1 层设计可以不要稳定 ABI、跨边界内联特化，可能更小更快。
**所以本实验给出的是「1 层成本的上界」和「2 层的准确值」。** 上界足够决策，
但结论不得写成"1 层一定更差"。

## 2. 最小实验内容

刻意做小到能做完，又刚好能量出斜率。

| 维度 | 选择 | 理由 |
|------|------|------|
| **ISA** | 只做 x86_64 | ISA 不是本次要比的轴（见 §0 已确定第 2 条） |
| **OS** | **先 Linux，再加 Windows** | 二者差异最大，斜率最诚实；macOS 不做 |
| **适配** | 一个：读文件 | 够触发 syscall/符号解析/FFI 三条路径 |
| **载荷** | 两个：① 纯计算（不碰 OS）② 读文件→哈希→打印 | ① 量地板，② 量总交付 |

**实验的信息量全部集中在「加 Windows」那一步**，前面都是准备工作。
如果时间只够做一件事，做那一步。

### 实现语言

不限，但必须能产出**可测量字节数**的原生产物（Rust / Zig / C 皆可）。
不要用需要运行时的语言——那会污染①②两个指标。

## 3. 判据（**必须在动手前认，事后不得改**）

> 整个命题是关于**增长曲线**的，不是关于今天有多小。
> **一个今天小但线性增长的设计，输给一个今天略大但持平的设计。**
> 所以 ③④ 比 ①② 重要。

| # | 判据 | 度量方法 | 性质 |
|---|------|----------|------|
| **①** | **地板高度** | 载荷①（纯计算）跑起来所需的**全部字节**（内核 + 必需伴随物）。2 层若能只靠内核跑，此值 = 内核大小 | 截距 |
| **②** | **总交付** | 载荷②（读文件哈希打印）在裸机上跑起来的**全部字节** | 截距 |
| **③** | **+1 个 OS 的边际成本** | 从 Linux-only 到 Linux+Windows：**新增字节数** 与 **改动行数**（`git diff --stat`），且分别记录「内核内」与「内核外」 | **斜率（决定性）** |
| **④** | **+1 个能力的边际成本** | 再加一个能力（建议：起子进程）时的同样两个数 | 斜率 |
| **⑤** | **TCB 大小** | 必须被信任/验证的字节数（1 层 = 整个产物；2 层 = 仅内核） | 安全 |
| **⑥** | **并存性** | 同机两个程序能否用同一适配包的**两个不兼容版本**。可以/不可以 | 库 vs 运行时的真分界 |

### 度量纪律

- 字节数一律取 **strip 后的 release 产物**，并记录编译器与 flag（否则不可比）
- ③④ 的「改动行数」不含测试与文档
- 每个数字必须能被第三方复跑；把复跑命令写进结果文件

### ⑥ 为什么单列

很多系统看起来是"库"，但因为全局单例、必须版本一致，实质上是运行时。
**版本可并存性才是库和运行时的真正分界**——比"它叫什么"可靠得多。

## 4. 判决规则与 kill criterion

**事前写死，避免事后凭手感或沉没成本选。**

1. **主判据是 ③**。若某变体在 ③ 上「内核内新增字节 > 0 且随 OS 数增长」，
   它就是向外增长，**直接判负**，不看其它指标。
2. 若 ③ 打平，看 ②（总交付）。
3. ② 也打平，看 ⑤（TCB）与 ⑥（并存性）——此时偏好 2 层。
4. **时间盒**：做到「加完 Windows 并量出 ③」为止。**在此之前不做 ④，不做 macOS，
   不做第二个 ISA，不做优化。**

### 失败模式警告

这类系统探索最常见的死法**不是选错方案，而是两个方案都变成休眠模块**——
范围不断扩张、始终差一点能量出结论、最后谁也没被证伪。

所以：到 ③ 量出来为止，**不许扩范围**。量完就停，写结果，等人决策。

## 6. 已排除的选项（不要重新提出）

| 选项 | 为什么排除 |
|------|-----------|
| **写两个独立原型** | 90% 的工作共享；两份实现会引入「哪个花的时间多」这个混淆变量，且成本翻倍 |
| **一层 + 封装（Cosmopolitan 路线）** | 它成立，但代价是**给你一个 POSIX**——正是本命题拒绝的封装。**不能同时要「不封装」和「一层」** |
| **发明中间 ISA / 字节码消除 ISA 轴** | 那就是发明字节码 = JVM 陷阱；且栈机为效率必然长出运行时 |
| **只做一个 OS** | **量不出 ③**，而 ③ 是决定性判据。只做一个 OS 的实验没有信息量 |
| **顺手做 macOS / 第二个 ISA** | 超出时间盒；ISA 轴已由 §0 第 2 条排除在本次讨论外 |

## 7. 本实验**不**回答的问题

记在这里，避免被顺手扩进来：

- **中立 IR 该长什么样**（L3 载荷表示法）。这是决定成败的下一个问题，
  但它独立于层数，应当单独设计。已知坑：**IR 从来没有它看上去那么目标中立**——
  Apple Bitcode 提交计划失败正因 LLVM IR 里烘焙了 ABI、类型尺寸、对齐、结构体布局。
- **降级逻辑（IR→原生码）放核内还是核外**。它决定「最小化 TCB」还是「最小化总交付」
  这两个不同的最优解。**本实验的 ⑤ 会给这个问题提供数据，但不替它做决定。**
- **第二层的组合机制**（如何让适配包可复用而不被钦定）。这是这条路上最难、
  且真正未解的问题——「不封装」把可移植性工作**转移**了而非消灭，
  失败模式是碎片化（JVM 的镜像失败）。形状取决于层数结论，所以放在本实验之后。
- **可验证性**：内核是"给二进制包就执行"的引擎，对自我进化系统这是无法验证的执行面
  （Thompson 的 trusting-trust 问题在 agent 自产代码时被放大）。已知的公开技术解法是
  **diverse double-compilation**：同一份源经两条独立路径产出，结果须字节级一致。
  在动态核里的形态应是「同一份中立 IR 经不同路径降级，必须**行为等价**」，
  且应当是**结构性不变量而非事后检查**。

## 8. 实验结论回填（2026-08-08，实测）

实现落在 `research/dynamic-core/`；完整数字与复跑命令见该目录 `RESULTS.md`。
以下是回填要点与**与本规格的实际偏离**。

### 判决结果：③ 打平 → 层数不由 ③ 决定

- **③（决定性判据）在两个变体上打平。** 从 Linux-only 到 Linux+Windows，
  **已交付的那个 OS 的产物字节增长 = 0**（Windows 代码全在 `cfg` 门后，Linux
  产物验证为逐字节不变）。内核**不为增加能力而变大**——文件 I/O 在适配器/载荷里，
  不在内核里。故按 §4.1「内核内新增字节 > 0 且随 OS 数增长 → 判负」，**两个变体都不判负**。
  两变体共用同一份 `core/kernel.rs`，加 Windows 的**内核内行数成本也完全相同**。
- ③ 打平 → 按 §4.2 看 **②（总交付）**：1 层 ≤ 2 层（Linux 少 392 B；Windows 因
  PE 对齐打平）。**按 §4 字面，微弱指向 1 层。**
- ⑤（TCB）与 ⑥（并存性）偏好 2 层，但 §4 只在 ② 打平时才看它们，而 ② 未打平。

**净结论：本实验没有量到「1 层会向外无界增长」（那本会判 1 层负），也没有量到
2 层在 ③ 上的优势（那本会为 2 层背书）。层数之争在决定性判据上是平局，最终成了
价值取舍**：要最小体积选 1 层；要「TCB 冻结 + 版本可并存」选 2 层。这可能与直觉相反，
但正是实验的价值——如实报。

### 六个数字（strip 后 release；x86_64；rustc 1.97）

| # | 判据 | 1 层(A) | 2 层(B) | 备注 |
|---|------|--------|--------|------|
| ① | 地板(pure) | 2512(L)/3584(W) | 2904(L)/3584(W) | B 含 loader+blob |
| ② | 总交付(rhp) | 3104(L)/4608(W) | 3496(L)/4608(W) | 1 层 ≤ 2 层 |
| ③ | +1 OS | **既有OS二进制 +0 B（两变体）**；内核内 +123/−2 行（共享，两变体相同）；核外 +55 行(win 适配器)+8 行(pack) | 决定性判据打平 |
| ④ | +1 能力(起子进程) | 非使用者 +432 B(L)/+512 B(W)（真·单产物 fused）；每能力线性 | **非使用者 +0**（新能力=独立 blob；文件载荷 blob 逐字节不变） | **不打平——首个能区分两变体的判据；偏 2 层**（补测，见下） |
| ⑤ | TCB | 整个产物 2.5–4.6 KB，随载荷增长 | **仅内核 ~2.7 KB(L)/~3.4 KB(W)，恒定** | 偏好 2 层 |
| ⑥ | 并存性 | YES（靠完全复制） | YES（共享冻结内核 + 独立版本 blob 文件） | 均无 JVM 式单例失败 |

**③ 的内核内/内核外拆分**：内核内字节增长（对既有 OS）= 0；内核内**行**增长
+123/−2（Windows 原语块 + 两个 Windows 入口 + 对既有 Linux 函数补的 cfg 守卫），
两变体共用故相同；核外 = `adapters/windows/readfile.rs`（新 55 行）+ pack 适配器选择（8 行）。

### ④ 补测（2026-08-08 后续跑）：**首个不打平的判据 → 偏 2 层**

上一轮遵守时间盒跳过 ④，并预判「④ 很可能是唯一还能区分两变体的判据」。补测证实了这一点。
第二个能力 = **起子进程并等它、报退出码**（Linux `fork`/`execve`/`wait4` 走 ③ raw_syscall；
Windows `CreateProcessA` + `WaitForSingleObject` + `GetExitCodeProcess` 走 ③ sym + ④ call）。
新载荷 `spawn_echo`（打印 `exit=07`、退出码 7），Windows **已执行验证**（A/B 两变体皆对，
无回归），Linux 交叉编译**只量字节**（本机无 WSL，沿用上一轮处理）。完整数字见 `RESULTS.md` §④。

- **(a) 能力本身**：2 层 = 一个独立 `blob_spawn`（439 B(L)/856 B(W)），只有起子进程的程序才加载；
  1 层独立程序 `A_spawn` 比地板多 272 B(L)/512 B(W)。
- **(b) 不使用该能力者的增长**——拆成两块，指向相反：
  - **(b1) 能力适配器的负担**：**2 层 = +0**（文件载荷 `blob_rhp` 逐字节不变，起子进程是另一个
    blob 文件）；**真·单产物 1 层 = +432 B(L)/+512 B(W)**（`A_fused − A_rhp`：只读文件的一次运行
    仍背着起子进程适配器）——**每加一个能力线性增长，压在每个程序上**。1 层要做到 +0，只能放弃
    「单产物」改成按载荷各编一个二进制，代价是把 ~2.7 KB 内核复制进每个二进制（即 ⑥ 的
    「靠复制实现并存」）。**只有 2 层能同时做到「能力隔离」与「共享一份内核」。**
    这正是判据 ①–③ 里从未出现、而 §3 认定最重要的「向外增长斜率」——**首次量到，且偏 2 层**。
  - **(b2) 共享内核被迫增长（诚实的意外成本）**：`CreateProcessA` 要 **10 个参数**，而 ④ `call`
    出厂时**卡在 7 参**（纯寄存器臂）。加这个能力**逼着改内核**——`call` 臂表 7→11。此代码在
    `core/kernel.rs`，**两变体都内联它**，故**每个含内核的产物都涨了** +208 B(L)/+512 B(W)，
    包括不起子进程者、以及 2 层那个「**冻结**」内核（`B_kernel_*`；载荷 blob 不含内核故 +0）。
    **没有加第五类原语**，但 ④ 出厂并非完全体（臂受限）；第二个能力把它逼到完体——这是**一次性台阶，
    不是每能力的斜率**（④ 一旦够通用，后续 ≤11 参能力内核内成本 = 0）。按 §1.1 要求**如实记录，未偷偷加**。

**④ 是否改判上一轮结论？** 上一轮：③ 打平 → 落 ② → 微弱偏 1 层（仅凭体积截距）。
- **按 §4 字面判决树**（只列 ③→②→⑤/⑥，从未把 ④ 列为节点）：结论不变，仍微弱偏 1 层。
- **按 §3 明写的优先级**（斜率 ③④ 高于截距 ①②：「今天小但线性增长的设计，输给今天略大但持平的」）：
  ③ 打平，但补测的 **④ 斜率不打平、偏 2 层**（每能力 0 增长且不复制内核），与 ⑤（TCB）、⑥（并存性）
  同向。1 层仅剩的优势是 ② 的原始体积截距。**按实验自己的判据排序，天平移向 2 层。**

**净结论（补 ④ 后）**：设计上「决定性」的 ③ 反而非决定性；上一轮延后的 ④ 才是分开两变体的那一条，
且偏 2 层——同时也暴露「加能力仍可能触碰共享内核」（当它逼原语提升通用度时；一次性，两变体同担）。
**未为让结论好看而改度量。** 若你只认 §4 字面树，仍是微弱 1 层；若你认 §3 的斜率优先，则是 2 层。

### 与规格不符之处（必然有）

1. **顺序反转为「先 Windows 跑通、Linux 交叉测量」**：本机无 WSL 发行版，Linux 产物
   只能构建+量字节、**不能执行**；Windows 产物已构建并**运行验证**（A/B 两变体
   read_hash_print 输出一致 `a49d2cbecc13994f`，与独立 Python 参考一致；pure exit=163）。
   两 OS 均覆盖、③ 可量——符合封面要求。
2. **变体 A 也走原语表**（§1.3 已知偏差）：故 A 是 1 层成本的**上界**，B 是准确值。
3. **变体 B 载荷 blob 在两 OS 上统一用 sysv64 ABI**（按 ELF 目标编译、
   `ld.lld --oformat binary` 展平；PE 展平不可靠）。内核 ④ `call` 在调 OS 函数时
   做 `sysv64→win64` 桥接。Windows 实测正确。红区警告：sysv64 有 128B 红区、Win64 没有，
   短叶子载荷未出问题，硬化构建应关红区。
4. **④ `call` 只覆盖整数/指针字子集**（无浮点/结构体/值返回）。出厂 ≤7 参；④ 补测时为
   `CreateProcessA`（10 参）**升到 ≤11 参**——仍是寄存器/栈字子集，非完整 libffi 描述符。见 §8 ④(b2)。
5. **未加第五类原语**：四原语在两 OS、两载荷上均自足；§1.1 警告的「加第 5 条的冲动」
   未出现。记为发现。
6. **载荷缓冲经原语 ① 申请**：RX 映射的扁平 blob 不能用静态 `.bss`（不可写），故
   `read_hash_print` 向 `mem_alloc` 要缓冲——更贴合模型，且暴露了一个真实的 2 层约束。
